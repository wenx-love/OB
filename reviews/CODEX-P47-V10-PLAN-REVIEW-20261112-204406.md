## P01：LOCK.tmp + rename 不能证明独占获取

**CONFIRMED 设计问题，P1，实施前必须更正。** PLAN:95。

普通 rename 的原子替换，不等于“目标已存在即失败”的独占安装。Node rename 可替换既有目标，不能跨 Windows/Linux 以 EEXIST 作为可靠互斥前提；使用固定 LOCK.tmp 还引入共享临时名竞争。完整 token 解决的是身份描述，不能代替互斥原语。

修订要求：明确选择有原子“已存在即失败”语义的获取方式，例如适用平台的 OS 锁、原子目录创建，或保留 O_EXCL/wx 并对未初始化记录保守拒绝。若使用候选文件安装，必须规定唯一候选名及可靠的 no-replace 安装语义，不能用普通 rename 代替。陈旧锁回收与释放还须有所有权和竞态规则；不能自动删除解析失败的活锁。测试应覆盖初始化、持有、回收和释放交错。

## P02：journal/CURRENT 的等式必须按事务状态定义

**CONFIRMED 条文矛盾，P1，实施前必须更正。** PLAN:102-105。

统一要求 `journal.files.new == CURRENT.files` 会拒绝正常回滚：事务 A→B 回滚后 journal.new 仍描述 B，而 CURRENT 应指向 A。首次发布回滚的 old_current=null 则允许没有 CURRENT。当前要求会把合法恢复判错。

修订要求：交付逐状态不变量表，至少包括 prepared、switching、pending-acceptance、committed（若保留）、verified、rolled-back、rollback-failed、未初始化。分别定义 CURRENT 指向、物化树允许状态、new/old 索引、backup/staging、锁、状态查询结果与退出码。verified 对比 new；rolled-back 对比 old_current/old 文件状态，并检查本次新增文件已按合同移除；中间态不得以全新索引相等冒充验证成功。缺 journal 应在“已初始化发布根”被拒，不能使全新未初始化根无法表达。

## P03：copy 与 rename 的权限及字节语义不能合并

**CONFIRMED 设计问题，P1，实施前必须更正。** PLAN:68、:77-82。

copy 不会删除源，不能像 rename 一样要求源删除/改名写权限，否则会拒绝从只读 ORIGINAL 合法复制的操作。rename 才需源改名/删除授权及源保护验证。二者都需要源读和目的授权，并分别验证前后对象状态。

字段表还把 create/overwrite 都列为允许 absent/exists，削弱 CreateNew 的存在性约束；又把 rename/copy 的 bytes_written 一概设 null，丢失文件 copy 的字节计量。

修订要求：按具体操作拆开：CreateNew 必须 absent（允许已存在的目录创建另设操作）；overwrite 应明确已存在/可创建的具体合同；append 定义增量；rename 验证源消失、目的对象身份/内容一致；copy 验证源保持及目的大小/摘要、文件复制量。目录 copy 应逐文件或用明确聚合清单计量，不能统一无字节证据。新增“只读源 copy 成功、同源 rename 拒绝”的区分性正负例，以及合法 rename/覆盖冲突例。

## P04：执行失败不能标 UNVERIFIED

**CONFIRMED 结果语义错误，P1，实施前必须更正。** PLAN:159；亦与 RESPONSE 的 Q12“不通过标 FAIL”相冲突。

已经执行、断言失败的阶段必须保留 FAILED/FAIL 结果。未执行、未到达、环境阻断或证据不足才是 UNVERIFIED（亦可更细分 NOT_RUN/NOT_REACHED/BLOCKED）。同一场景可以既有已确认失败项，又有尚未验证的后续项，不能用一个未验证标签抹去失败。

修订要求：定义结果枚举、状态传播、计数及退出码；修复后新运行另存，既有失败证据不覆盖。中止后未执行检查不算通过，不将失败改称未验证。

## P05：pending-acceptance 必须补全生命周期和持锁接口

**CONFIRMED 规格缺项，运行正确性 UNVERIFIED；P1，实施前需闭合。** PLAN:89-91。

把 post gate 放入持锁会话是合理方向，但尚未规定 pending 时进程崩溃、recover、重复 publish、status、accept 的规则及接受持久点。undo“持锁”也须明确复用现有会话还是重新取锁，避免自锁。原有 checker 若仍只接受 journal=verified，持锁 pending 的正常内部 gate 将永远失败。

修订要求：明确会话API及 txid/rid/所有权绑定；内部只读 gate 如何验证期望 pending 事务，与外部“已接受 verified”区分。accept/undo 共用正确会话且身份不符零写入；noop 没有本次可撤销事务；accept 前中断不能只因字节吻合就被 recover 擅自升级 verified。规定各中断点的回滚/拒绝/重验证政策、释放失败处理和单独证据。状态规则与 P02 使用同一份协议。

## P06：输入可用性不能等同于“有 ok 生产者”

**CONFIRMED 验收规则不完整；P1，实施前需闭合。** PLAN:46-53。

批准的外部输入、运行前已存在输入没有运行内 producer；producer=ok 也不能替代文件实际存在、身份和摘要核验。failed producer 还可能留下必须如实报告的部分证据。仅以“非 optional 输入有 ok 生产者”判定会同时过严和漏检。

修订要求：为外部批准输入、运行前输入、生成输入分别定义存在性/完整性/授权条件及可消费状态；C17 等失败报告必须披露 skip/缺失/部分内容。逐路径证明必要输入可满足。明确 finalizer 与 before/after 的例外状态机，不能仅新增一句文书例外而不修改 replay/向量。

## P07：无可信 close 与片段 seal 的边界仍需明确

**CONFIRMED 规格缺项；P1，实施前需闭合。** PLAN:36、:57-59。

链已损坏或 dispatcher 死亡时，可能不能可信追加 close，因此不能只从“已发生 close 的 code”推导安全停止。另 fragment-seal 仅禁止 sealed-full 不够：片段同样不能伪装为权威 aborted/degraded-prefix 全运行封存。

修订要求：定义可信链证据与链外 launch/operator 失败记录的来源、身份、摘要及证明边界；链损坏拒绝权威封存、保留原始链。fragment 采用明确的非权威fixture类型和独立validator入口，任何终端模式都不能绕过完整链要求。orphan 的 abort 原因须正式建模，不能简单把字符串改成 C10-N/orphan 却不修 failure_class 枚举与派生规则。

## P08：恰好一错与至少一条断言都不是通用验收标准

**CONFIRMED 判据过宽；P2，证据设计需在实施前修改。** PLAN:123、:145。

“每场景至少一个能失败的断言”仍可能只检查 child 非零，未证明目标故障。“所有负例恰好一个错误码”只适合基底已独立通过、单缺陷注入的单元向量，不能用于压制复合/端到端故障应报告的多项错误。

修订要求：单缺陷fixture先证明有效基底；复合故障验证完整预期错误集合或明确的因果主错误及后续诊断。每个实验同时核对 requested/reached/observed、精确触发原因、故障现场、事务身份、恢复结果及最终一致性，按适用性逐项列出。NOT_REACHED 独立计数；不能要求恰好一错而减少必要检查。
