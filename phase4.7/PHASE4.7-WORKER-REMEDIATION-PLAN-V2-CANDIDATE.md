## 三、已批准决策的落实（不得重开）

### 3.1 D3：有界延后队列

**取值（逐字）：**

- 队列上限 **256 条**。
- 累计源码大小上限 **64 MB**。
- 引入第四种状态 **`deferred`**。
- 按发现顺序补投。
- 不超过 **64 KB** 的小脚本优先。
- 只持有脚本对象引用，不复制源码。
- `cancelAll` 和纪元变更时显式结算所有旧任务。
- 禁止静默丢弃。
- 被拒绝、延后、执行、成功提交必须分别统计。

**V2 的落实定义：**

| 项 | 定义 |
|---|---|
| 预算覆盖的集合 | **延后集合**：已受理但尚未开始执行的逻辑请求。执行槽位固定 1；不存在第二个无界队列 |
| 条数口径 | 延后集合中的逻辑请求数 ≤ 256 |
| 字节口径 | 每个逻辑请求的源码按 **UTF-8 编码后的字节数**计；不是 UTF-16 长度，不是字符数 |
| 单条超预算 | 单份源码 > 64 MB：不受理，返回显式错误 `source-too-large`，计入 rejected，不缓存，不静默丢弃 |
| 容量用尽 | 新增会让条数或字节超过上限：不受理，返回显式错误 `deferred-full`，计入 rejected，面板显示“延后已满 N 条 / M 字节”，不缓存；用户刷新后可重试 |
| 延后进入 | `analyze()` 受理后，若执行槽位被占用，进入 `deferred` |
| 补投 | 执行槽位结算（成功、失败、取消）后，按 §6.2 的调度规则取下一个 |
| 小脚本优先 | 延后集合内分两条 FIFO：小脚本（≤64 KB）与其余；先清空小脚本队列，再取大脚本队列 |
| 发现顺序 | 同一优先级内严格按发现顺序（逻辑请求序号）；展示顺序始终按发现顺序，与调度顺序分离 |
| 饥饿 | 连续小脚本会使大脚本等待；V2 只**记录**每个延后项的最大等待时间和“被小脚本连续越过次数”，不改变已批准的优先级；若实测饥饿，另行申请决策 |
| 取消/纪元 | `cancelAll` 或纪元变更时，延后集合逐项显式结算为 `cancelled`，清空引用与等待者；不触发新补投 |
| 统计 | 面板分别计数：`rejected`、`deferred`（当前值）、`executing`（0/1）、`committed`、`analysis-failed`、`commit-rejected`、`cancelled`、`retry-pending` |

**禁止：** 保留“取消上限”的备选；把延后计为已分析；把 `deferred-full` 静默丢弃；把延后项源码再复制一份。

### 3.2 D4：挂死看门狗与性能判据分离

**取值（逐字）：**

`clamp(120s + 1.0ms × 源码字节数, 5min, 45min)`

**V2 的落实定义：**

| 项 | 定义 |
|---|---|
| 阈值登记 | 每个输入（参考夹具与真实样本）在测量前登记；登记表写入阶段证据；测量后不得修改 |
| 源码字节数 | 源码字符串按 UTF-8 编码后的字节数，与 D3 同一口径 |
| 计时起点 | 尝试被派发到 Worker 的时刻（`postMessage` 返回后开始计时） |
| 计时终点 | 该尝试的 Worker 回复到达、或看门狗触发、或崩溃事件到达 |
| 触发动作 | 置该尝试为超时 → `terminate()` 当前 Worker → 创建新 Worker → 自动重试 1 次 |
| 第二次失败 | 显式失败 `watchdog-timeout-retry-exhausted`，不缓存，不无限重试 |
| 50% 门槛 | 所有**合法完成**的任务（不含故障注入、不含被取消、不含被拒绝）耗时必须 < 阈值的 50%；任一 ≥50% 即该阶段性能验收不通过 |
| 禁止 | 用“阶段四实测最大值的 6 倍”或“30 分钟下限”替代公式；测量后改阈值；把看门狗当成性能上限 |

**性能判据与看门狗分离：** 看门狗只回答“是否挂死”；性能验收回答“是否足够快”。两者使用不同的证据与不同的失败码。

| 独立审查（只读） | `WENX\CodexSandboxOffline` / `OnLine` | 无（只读） | 全部写入 | 读取 `<run>`、审查包、证据；不得在同一根执行写入式 W2 |
| 构建/测试子进程 | 继承实施执行身份 | 由启动器与守卫限制在上述目录 | 同上 | esbuild 原生进程、Chrome、`cmd` 不受 Node 守卫约束，靠位置与启动器 |
| 提升执行 | 经用户授权的管理员 | 原项目（仅 Gate P 的批准清单） | 其余一切 | 不在原项目运行构建/测试 |

### 4.2 W2 的两种模式

Codex 要求“独立验证”，但只读身份不能在同一个根里执行写入式验证。V2 明确两种模式，默认 A：

| 模式 | 执行者 | 位置 | 允许的动作 | 产物 |
|---|---|---|---|---|
| W2-A（默认） | Codex，只读 | 读取 `<run>` 与审查包 | 读代码、读清单、读日志、复算哈希、静态对照 | 审查意见；不产生写入 |
| W2-B（需单独授权） | 用户授权的独立执行者 | 独立的 `D:\P47RUN\w2-<id>`（自己的 ACL） | 在自己的根内应用补丁、复跑该阶段验收 | 独立证据包 |

**禁止：** 为让 Codex 执行 W2-B 而给 Codex 沙箱组写权限；复用 V0 的 TEMP 例外作为正式阶段例外。

### 4.3 权限冲突的处理

- 原项目当前的宽泛写权限（继承的 Authenticated Users、显式沙箱组）在 Gate P 之前**不修改**；只在基线中记录，并在静默窗口中约定不使用。
- 运行根由实施执行者创建并设置 ACL；Codex 只读；读不到时按 D14 的替代方案处理，不扩权。
- 任何 ACL 变更都必须有用户书面授权；V2 不包含任何未经授权的 ACL 变更。

## 五、任务状态机与结算协议（R01–R04、R10）

### 5.1 状态定义

**逻辑请求状态（客户端）：**

| 状态 | 含义 | 是否有 Promise 未结算 | 允许的下一状态 |
|---|---|---|---|
| `deferred` | 已受理，等待执行槽位 | 是 | `executing`、`cancelled`、`failed`（熔断/关闭） |
| `executing` | 某次尝试在飞行 | 是 | `retry-pending`、`completed`、`failed`、`cancelled` |
| `retry-pending` | 首次尝试失败、等待第二次派发 | 是 | `executing`、`failed`、`cancelled` |
| `completed` | 结果已交付（分析成功或解析失败） | 否 | — |
| `failed` | 显式错误已交付 | 否 | — |
| `rejected` | 未受理（容量、超预算、熔断、关闭） | 否（立即返回） | — |
| `cancelled` | 被 `cancelAll`/纪元变更结算 | 否 | — |

**尝试状态：**

| 状态 | 含义 |
|---|---|
| `dispatched` | 已 `postMessage`，看门狗计时中 |
| `settled-success` | 收到匹配回复 |
| `settled-error` | 收到匹配错误回复 |
| `timed-out` | 看门狗触发 |
| `crashed` | `onerror`/`messageerror` |
| `post-failed` | `postMessage` 抛错 |
| `ignored-stale` | 事件不属于当前尝试/Worker/纪元，忽略 |

### 5.2 结算责任

| 事件 | 谁结算 | 结算内容 | 是否重试 | 是否计数熔断 | 是否写缓存 |
|---|---|---|---|---|---|
| 构造 Worker 抛错 | `ensureWorker` | 当前逻辑请求 failed(`worker-unavailable`)；延后集合全部 failed(`breaker-open`) | 否 | 是 | 否 |
| `onerror` | Worker 事件处理器 | 当前尝试 crashed → 逻辑请求重试或 failed | 首次是 | 是 | 否 |
| `messageerror` | 同上 | 同上 | 首次是 | 是 | 否 |
| `postMessage` 抛错 | `dispatch` | 当前尝试 post-failed → 重试或 failed | 首次是 | 是 | 否 |
| 看门狗触发 | 计时器 | 当前尝试 timed-out → terminate → 重试或 failed | 首次是 | 否（单独计数） | 否 |
| 匹配回复成功 | `onmessage` | completed(result) | 否 | 否 | 是（成功） |
| 匹配回复解析失败 | `onmessage` | completed(analysis-failed) | 否 | 否 | 是（确定性失败） |
| 回显不一致 | 面板提交校验 | commit-rejected | 否 | 否 | 否 |
| `cancelAll` | 取消协议 | 全部 cancelled | 否 | 否 | 清空 |
| `dispose` | 取消协议 | 全部 cancelled，disposed | 否 | 否 | 清空 |

**关键约束：**

- 每个逻辑请求恰好结算一次；任何路径都不得二次 `resolve`。
- 任何非终态都必须有明确的拥有者：延后集合条目、看门狗、重试队列或取消协议。
- 失败必须带错误码；不得只写自然语言。
- 首次失败必须可见：日志记录 `attempt-failed`（含 attemptId、错误码、耗时）；统计记录 `attemptFailures` 与 `retrySucceeded`，不用重试成功抹去首次失败。

### 5.3 批量取消协议（R02）

`cancelAll(reason, { epochChanged })` 的固定顺序：

1. 置 `cancelling = true`；`schedulerGeneration++`；禁止 `pump`。
2. 若 `epochChanged`：`pageEpoch++`；标记所有旧纪元请求失效。
3. 结算在飞行尝试：清看门狗；标记 `cancelled`；`terminate()` 当前 Worker；解除全部处理器。
4. 结算全部延后项：逐个 `resolve(failed('cancelled'))`；清空延后集合、等待者、定时器引用。
5. 清空 `active`、重试队列、请求表。
6. 清空缓存（纪元变化必须清；面板关闭同样清）。
7. 置 `cancelling = false`；允许后续请求重新 `pump`。
8. 日志记录取消原因、结算数量、是否纪元变化。

**禁止：** 在批量取消期间 `pump` 新任务；把取消当作成功；取消后延迟回调再次 `pump`。

### 5.4 熔断（R03）

| 项 | 定义 |
|---|---|
| 计数单位 | **Worker 级失败**：构造失败、`onerror`、`messageerror`、`postMessage` 抛错；连续 3 次触发熔断 |
| 不计入 | 看门狗超时（单独计数）；解析失败；回显不一致；用户取消 |
| 熔断时已执行任务 | 当前尝试已失败并结算；已成功的任务不受影响 |
| 熔断时排队任务 | 延后集合逐项 `failed('breaker-open')`，清空；不得留 permanent pending |
| 熔断时延后任务 | 同上；面板计数 `rejected` 或 `failed`，二者只取其一，按“是否已受理”区分 |
| 熔断时等待者 | 随对应逻辑请求一起结算，不单独悬挂 |
| 恢复 | `refresh`、新纪元或 `cancelAll` 调用 `resetBreaker()`；重置计数与标志；下一次 `pump` 重新创建 Worker；若再失败则重新熔断 |
| 可见性 | 面板显示熔断状态、失败次数、最后错误码；不自动重试到无限 |

### 5.5 旧 Worker 事件与代次绑定（R04）

每个异步回调必须绑定：

- `workerGeneration`：每次创建/退役 Worker 递增；事件所属代次不等于当前 → 忽略。
- `pageEpoch`：页面纪元；不等于当前 → 忽略。
- `attemptId`：尝试编号；不等于当前 → 忽略。
- `logicalRequestId`：逻辑请求；不等于当前 → 忽略。

需要绑定的回调包括：`onmessage`、`onerror`、`messageerror`、看门狗定时器、哈希 Promise、重试派发、延后补投、缓存写入。失效回调只能记日志，不得改状态、不得 `pump`、不得写缓存。

### 5.6 重试矩阵（R10）

| 失败类型 | 首次 | 第二次 | 最终错误码 |
|---|---|---|---|
| 看门狗超时 | 重试 1 次 | 失败 | `watchdog-timeout-retry-exhausted` |
| Worker 崩溃/`messageerror`/发送失败 | 重试 1 次 | 失败 | `worker-crashed-retry-exhausted` |
| 构造失败 | 不重试（无 Worker） | — | `worker-unavailable` |
| 解析失败（业务） | 不重试 | — | `analysis-failed` |
| 回显不一致 | 不重试 | — | `commit-rejected` |
| 取消/纪元变化 | 不重试 | — | `cancelled` |
| 延后容量/超预算 | 不重试 | — | `deferred-full` / `source-too-large` |

**约束：** 重试使用新的 `attemptId` 和新的 `workerGeneration`；旧的看门狗、处理器、哈希 Promise 必须先失效；重试期间逻辑请求仍是一个，等待者仍挂同一个 Promise。

### 5.7 不变量

1. 每个逻辑请求恰好结算一次。
2. `inflight ≤ 1`。
3. `deferred` 条数 ≤256 且 UTF-8 字节 ≤64 MB。
4. `cancelling` 期间 `pump` 不执行。
5. 任何非终态都有拥有者。
6. 旧代次事件无副作用。
7. 缓存只在成功或确定性解析失败时写入；基础设施失败、取消、熔断、超时不写。

## 六、队列、延后、缓存与统计（R05–R08）

### 6.1 队列结构

只有一个执行槽位和一个延后集合：

```text
                 ┌──────────────┐
  analyze() ───▶ │ deferred 集合 │ ──pump──▶ 执行槽位（1）──▶ Worker
                 │ ≤256 条       │              │
                 │ ≤64 MB 源码   │              └──▶ 结算
                 └──────────────┘
```

- 不存在第二个无界数组；不存在“队列 + 延后 + 重试”三个各自计数的结构。
- 重试不回到延后集合：逻辑请求在 `retry-pending` 时保留执行优先权，直接派发第二次尝试（不插队、不重新排队）。
- 缓存不属于队列；缓存只是结果复用。

### 6.2 调度规则

`pump()` 仅在以下全部成立时执行：未 `disposed`、未 `cancelling`、未熔断、`inflight === null`、延后集合非空。

取下一个的顺序：

1. 小脚本队列（源码 UTF-8 ≤64 KB）非空 → 取队首。
2. 否则取大脚本队列队首。
3. 同级内严格按逻辑请求序号（发现顺序）。
4. 展示顺序与调度顺序分离：面板列表、日志顺序始终按发现顺序；执行顺序按上述规则。

**饥饿记录：** 每个延后项记录 `enqueuedAt`、`lastOvertakenAt`、`overtakenBySmall`。若大脚本连续被小脚本越过超过阈值（技术参数，默认 64 次），只记录 `starvation-suspected` 并上报；不改变优先级。

### 6.3 容量与溢出

| 情形 | 处理 |
|---|---|
| 延后条数已达 256 | 新请求不受理：`rejected('deferred-full')`；面板显示当前条数与字节；不缓存 |
| 延后累计源码已达 64 MB | 同上 |
| 单份源码 >64 MB | `rejected('source-too-large')` |
| 延后项被取消/纪元变更 | 逐项 `cancelled`；清空 |
| 延后项开始执行 | 从延后集合移除，字节预算释放 |

**可见性要求：** `deferred-full` 和 `source-too-large` 必须在面板日志中带 scriptId 与当前计数；不得只写控制台。

### 6.4 统计口径

| 计数 | 含义 | 何时增加 | 何时减少 |
|---|---|---|---|
| `discovered` | 面板收到的脚本数 | 每条 `script-discovered` | 页面重置清空 |
| `deferred` | 当前延后集合大小 | 受理且未执行 | 开始执行/取消/熔断结算 |
| `executing` | 当前执行槽位（0/1） | 派发尝试 | 结算 |
| `retry-pending` | 首次失败、等待第二次 | 首次失败 | 第二次派发/取消 |
| `committed` | 结果已提交的脚本数 | 提交校验通过 | 页面重置/源码变化失效 |
| `analysis-failed` | Worker 返回解析失败 | 解析失败 | 页面重置 |
| `commit-rejected` | 提交校验失败 | 校验失败 | 页面重置 |
| `rejected` | 未受理（容量/超预算/熔断/关闭） | 立即返回错误 | 不减少（历史计数） |
| `cancelled` | 被取消结算 | 取消 | 不减少（历史计数） |
| `attempt-failures` | 尝试级失败次数 | 每次失败 | 不减少 |
| `retry-succeeded` | 重试后成功次数 | 第二次成功 | 不减少 |

**`analyzed` 的唯一含义：** `committed`。解析失败、提交失败、延后、执行中都不计入 `analyzed`。详见 §8。

### 6.5 缓存身份（R05）

缓存键必须覆盖：

```text
cacheKey = hash(
  pageEpoch
  | scriptId
  | sourceSha256
  | scriptUrl                // 原样字符串，不做宽松归一化
  | analyzerVersion          // discoverDecoders 语义版本；改动即递增
  | optionsHash              // 分析选项；当前为空也保留字段
)
```

- `pageEpoch` 覆盖页面/会话生命周期；页面重置即失效。
- `scriptId` 覆盖 CDP 脚本身份。
- `sourceSha256` 覆盖源码身份；同 id 换源码必然不同键。
- `scriptUrl` 覆盖 URL 身份；同 id、同源码、不同 URL 不复用。
- `analyzerVersion` 覆盖分析器实现变化。
- 等待者绑定**逻辑请求实例**，不按 scriptId 轮询。

### 6.6 缓存容量与淘汰（R06）

| 项 | 定义 |
|---|---|
| 条目上限 | 128 条 |
| 结果字节上限 | 32 MB（Worker 回复附带 `resultBytes`，按 JSON 序列化长度估算） |
| 淘汰策略 | LRU：优先淘汰最久未访问的**已完成**条目；不得淘汰有等待者或在执行的条目 |
| 淘汰后的行为 | 缓存只是复用优化；面板已提交结果不因缓存淘汰而丢失；再次请求会重新分析 |
| 失败缓存 | 只缓存确定性解析失败（`analyzed=false`）；基础设施失败、超时、崩溃、取消、熔断、容量拒绝一律不缓存 |
| 纪元变化 | 清空全部缓存 |
| 源码变化 | 新键自然隔离；旧键按 LRU 淘汰 |
| 统计 | `cacheHits`、`cacheMisses`、`cacheEvictions` 进入客户端统计与阶段证据 |

### 6.7 延后集合与内存

- 延后项只持脚本对象引用（`script`），不复制 `source` 字符串。
- 但延后项仍有：逻辑请求对象、Promise、等待者数组、入队时间等开销；不得在文档中声称“无额外内存”。
- 延后集合的上界（256 条 / 64 MB）只约束延后项；执行槽位、缓存、重试各按 §6.5、§6.6 单独约束。

## 七、页面纪元、刷新与后台迟到事件（R11、R12）

### 7.1 页面纪元 `pageEpoch`

- 只在页面级重置（导航/刷新/目标页关闭）时递增。
- 递增动作由面板的重置分支执行，且是唯一入口。
- 纪元变化后：旧纪元的一切分析结果、捕获记录、候选、提交标识全部失效。
- 刷新（手动刷新 decoder discovery）**不**递增 `pageEpoch`；它递增每个脚本的 `requestSeq`。

### 7.2 后台迟到事件守卫（D6，必修）

静态缺口（`CONFIRMED`）：`background.ts:228-239` 在异步 `getScriptSource` 返回后，不检查收集器是否仍持有该脚本；`panel.ts:1204-1205` 收到即写入并删除退休标记。

V2 要求：

1. **后台发送前校验对象身份**：`collector.getScript(scriptId) === script` 且 `scriptCollectors.get(tabId) === collector`；任一不成立即丢弃，不发送。
2. **后台附带收集器纪元**：每个 tab 的收集器维护 `collectorEpoch`，页面重置 `clear()` 时递增；`script-discovered` 消息携带 `collectorEpoch`。
3. **面板接收校验**：面板维护每个 tab 的 `latestCollectorEpoch`；收到小于当前值的消息丢弃；收到更大值时更新并继续处理。
4. **测试先行**：构造“异步取源码 → 页面重置 → 旧回调返回”的确定性测试，断言不发送/不接收；再加“正常脚本不被丢弃”的对照测试。
5. **真实浏览器频率**：`UNVERIFIED`。不得以“复现不了”为由取消修复；也不得声称该问题在真实站点高频发生。

### 7.3 刷新的事务性

`refreshDecoderDiscovery` 的固定规则：

1. 单飞：已有刷新在运行时不启动第二次。
2. 快照：取当前 `discoveredScripts` 的脚本对象快照。
3. 逐脚本：为每个脚本分配新的 `requestSeq`；提交时必须是该脚本的最新请求。
4. 不清空全局候选：旧结果保留到该脚本的新结果提交成功，再按脚本替换。
5. 源码变化：快照后源码哈希变化 → 该脚本本次刷新作废，旧结果标记 `stale-source`，不得作为捕获目标。
6. 纪元变化：中止刷新，丢弃全部旧请求。
7. 失败可见：每个失败带 scriptId 与错误码；完成后打印“刷新完成/部分失败/中止”的明确结论。
8. 提交成功：清除该脚本旧错误；更新 `committedSourceHash` 与 `requestSeq`。

### 7.4 捕获目标的有效性

构造捕获目标时必须同时满足：

- `analysisState === committed`。
- `committedSourceHash === 当前源码哈希`。
- `epoch === 当前 pageEpoch`。
- 未退休（D7 若获批则按 D7 过滤；未获批时保持现有行为，但身份失效的旧结果一律排除）。

**说明：** 身份失效排除不是 D7；D7 只涉及“退休脚本候选”的筛选与提示。两者分开记录。

## 八、`analyzed` 语义与面板状态（R13）

### 8.1 状态枚举

每个脚本对象有唯一的 `analysisState`：

| 状态 | 含义 |
|---|---|
| `discovered` | 已收到脚本，尚未提交分析 |
| `deferred` | 已受理，等待执行 |
| `executing` | 正在执行某次尝试 |
| `retry-pending` | 首次失败，等待第二次 |
| `analysis-succeeded` | Worker 返回成功，但尚未提交 |
| `analysis-failed` | Worker 返回解析失败（`result.analyzed === false`） |
| `committed` | 提交校验通过，候选已合并 |
| `commit-rejected` | Worker 成功但提交校验失败（纪元/身份/回显/源码变化） |
| `cancelled` | 被取消 |

### 8.2 `analyzed` 的唯一含义

- `script.analyzed === true` **当且仅当** `analysisState === 'committed'`。
- `analysis-succeeded` 不是 `analyzed`；它只表示 Worker 返回了结果，尚未过提交校验。
- `analysis-failed`、`commit-rejected`、`cancelled` 一律不是 `analyzed`。
- 面板“已分析”计数 = `committed` 数量，不是 `analysis-succeeded` 数量。

### 8.3 提交校验（同步块）

提交前依次校验，任一失败即 `commit-rejected`：

1. `epoch === 当前 pageEpoch`。
2. `discoveredScripts.get(scriptId) === script`（同一对象）。
3. 未退休（若 D7 未获批，仍保留现有退休判定）。
4. `requestSeq === 该脚本最新请求序号`。
5. 源码哈希未变（`sha256(script.source) === result.sourceSha256` 或与提交时快照一致）。
6. Worker 回显的 `scriptId`、`sourceLength`、`sourceSha256` 与期望一致。

提交成功后：

- 用本次候选替换该脚本旧候选（不是追加）。
- 按发现顺序原地重建 `allCandidates`。
- 清除该脚本旧错误。
- 内部记录 `committedAt`（不通过钩子导出）。

### 8.4 统计一致性测试

- 每个状态的脚本数之和 = `discovered`。
- `committed + analysis-failed + commit-rejected + cancelled + deferred + executing + retry-pending + discovered(未提交)` = 总数。
- 解析失败不计入 `committed`。
- 提交失败不计入 `committed`。
- 重试成功计入 `committed`，但 `retry-succeeded` 与 `attempt-failures` 仍保留。

## 九、看门狗、重试与验收分类（R09、R16、R18）

### 9.1 计时与阈值

- 公式：`clamp(120000ms + 1.0ms × UTF8字节数, 300000ms, 2700000ms)`。
- 登记：阶段四开始前，对每个参考输入计算并登记阈值；登记后不得修改。
- 计时：尝试派发 → 回复/崩溃/看门狗。排队等待、延后等待不计入尝试耗时。
- 重试：首次失败后第二次尝试重新计时，不继承首次剩余时间。
- 记录：每次尝试记录 `attemptId`、`startedAt`、`settledAt`、`elapsedMs`、`thresholdMs`、`outcome`、`errorCode`。

### 9.2 50% 验收

- 对每个合法完成的任务：`elapsedMs < 0.5 × thresholdMs`。
- 任一不满足：该阶段性能验收不通过；不得改阈值、不得删任务、不得把该任务标为“故障注入”。
- 故障注入任务、取消任务、拒绝任务不参与 50% 统计，但必须单独列出。

### 9.3 性能完成的三段状态（R16）

| 状态 | 判定 | 证据 |
|---|---|---|
| `workerCompleted` | 目标尝试的回复到达，且 `attemptId`/`requestId`/回显匹配 | 客户端统计/日志 |
| `commitCompleted` | 目标逻辑请求提交成功，钩子记录出现 `state=committed` 与 `committedCandidates` | D10 钩子快照（`requestSeq` + `committedCandidates`） |
| `renderCompleted` | DOM 中候选卡片数与 `#dec-candidates` 文本一致，且连续两次读取稳定 | DOM 读取（窗口结束后） |
| `resultUsable` | 以上三者 + 再次读取钩子确认同一脚本的 `requestSeq` 与 `committedCandidates` 未变 | 钩子 + DOM |

**原子性说明：** 钩子的一次读取只能给出同步快照；之后的导出、DOM 渲染、结果落地不是同一个原子操作。因此必须绑定同一个脚本的 `requestSeq`，并在渲染后复查 `requestSeq` 与 `committedCandidates` 没有变化。

### 9.4 修复前基线的弱判据

- 修复前构建是同步分析，用“候选名多重集合被卡片覆盖 + 总数不再变化”的弱判据；必须标注为弱基线。
- 不能因为“同步分析”就断言全局计数稳定等于全部完成。
- 若无法取得同口径的完整窗口，改善倍率记 `n/a`，不得用不同窗口的数字相除。

### 9.5 分类优先级（R18）

**目标层状态：**

| 状态 | 判定 |
|---|---|
| `target-completed` | 目标提交并渲染 |
| `target-analysis-failed` | 解析失败或提交失败 |
| `target-cancelled` | 用户/纪元取消 |
| `target-deferred-at-deadline` | 窗口结束时目标仍在延后，从未开始 |
| `target-executing-at-deadline` | 窗口结束时目标正在执行 |
| `target-missing` | 发现期限结束仍没有唯一目标 |

**运行层结论（互斥，按优先级从高到低）：**

1. `setup-failed`：目标缺失、不唯一、源码哈希不符、夹具/连接失败。
2. `cancelled`：用户取消或纪元变化。
3. `infrastructure-failed`：Worker 不可用、熔断、崩溃重试耗尽。
4. `execution-timeout`：看门狗触发且重试耗尽。
5. `queue-wait-timeout`：窗口结束时目标从未开始（延后/饥饿），不是 Worker 执行超时。
6. `window-deadline-during-execution`：窗口结束时目标正在执行，但看门狗未触发。
7. `target-failed`：解析失败或提交失败。
8. `partial`：目标完成，但其他脚本未完成。
9. `completed`：目标完成且其他脚本完成，窗口内无未结算项。

**规则：**

- 高优先级覆盖低优先级；`partial` 不得抢占失败结论。
- `target-missing` 只能在发现期限结束后定案；发现期限内不得提前判缺失。
- 排队等待与执行超时必须是两个不同的失败码。
- 同一 run 只允许一个运行层结论；目标层与运行层同时记录。

### 9.6 窗口与计时器节流

- 窗口定义：从页面导航开始，到目标 `resultUsable` 为止。
- 后台/被遮挡窗口的计时器节流会干扰长任务与时间戳；阶段四必须做一次漂移探针，记录是否受节流影响。
- 若无法消除节流影响，报告必须写明；不得把受影响的数据当作同口径对比。

1. 在 `<run>\out\build\a` 与 `<run>\out\build\b` 两个独立目录各构建一次，输入相同。

4. 扫描 `dist/**`：不得出现工作副本绝对路径、盘符路径、`file://` 形式、用户名路径。
5. 任一失败：阶段三不通过；不得用“只差一点”放行。

### 10.4 `dist` 校验脚本

只读校验五项：

1. 构建戳的输入清单与当前源码逐文件一致。
2. `panel.js` 引用的 Worker 产物存在，文件名与构建戳一致。
3. Worker 产物的格式特征与构造参数匹配。
4. `panel.js` 不含主线程的 `discoverDecoders(` 调用。
5. 四个入口文件齐全（background、devtools、panel、sandbox）。

负例：缺 Worker 文件、改动一个输入文件、把 Worker 产物替换成 IIFE 而构造仍是 module——三种都必须报错。

## 十一、只读钩子、独立取证与完整一致性（R17、R19）

### 11.1 生产钩子的边界

- 严格按 §3.3：只有 `?obTest=1` 挂载；字段白名单；不返回源码、候选内容、调用位置。
- 不得为完整结果比较而在生产钩子上新增“取已提交结果”“取源码”“取候选”方法。
- 键集合白名单测试必须覆盖：缺字段、多字段、字段类型、冻结、门控。

### 11.2 面板提交的验证

面板提交通过钩子验证：

- 目标脚本的 `state === 'committed'`。
- `committedCandidates` 等于参考值（例如 983）。
- `requestSeq` 与目标请求一致。
- `enqueuedAt ≤ startedAt ≤ settledAt`。
- 脚本记录对应的页面由运行装置记录；钩子本身不返回 `epoch`。
- 两个间隔 2 秒的钩子快照里，同一脚本的 `requestSeq` 与 `committedCandidates` 相同。

这只能证明“面板提交了多少”，不能证明“结果内容与 Node 完全一致”。内容一致性由 §11.3 的独立取证和 §11.4 的四方比较完成。

### 11.3 独立测试取证（不扩大生产钩子）

在隔离的测试环境中：

1. 一个**测试专用页面**（构建到 `<run>\out\harness`，不进入产品 `dist`）加载产品 `decoder-analysis-client` 与产品 Worker 产物；记录 Worker 产物哈希。
2. 用同一份夹具源码、同一 `scriptId`、同一 URL 发起分析。
3. 用类型保真编码器（见 §11.4）序列化**完整结果**。
4. 通过本机回环 POST 到测试服务，落盘到 `<run>\evidence`，独占创建。
5. Node 读取落盘全文，独立计算哈希；浏览器内哈希与 Node 哈希必须相等。
6. 该取证不使用面板 DOM，不使用生产钩子；它不是产品出口。
7. 阶段五的 Chrome 侧必须使用**产品 Worker 产物**，不是复制品；记录产物哈希。

### 11.4 完整一致性（R19）

- **类型保真编码：** 区分 `undefined` 与缺失、`-0`、`NaN`、`±Infinity`、孤立代理项；遇到函数、Map、类实例等不可序列化值时显式报错，不得静默丢弃。
- **两个哈希：** 每份输出计算
  - `hashOrdered`：保留键顺序；
  - `hashSorted`：键排序后计算。
- **比较规则：**
  - 四方（Node 主线程、Node 线程加载真实 Worker 入口、Chrome 主线程、Chrome 产品客户端驱动 `dist` Worker）各自的 `hashOrdered` 必须四方相等。
  - 各自的 `hashSorted` 必须四方相等。
  - **不要求** `hashOrdered` 等于 `hashSorted`；若不等，单独报告“字段顺序不同”，不作为失败。
- **完整深比较：** 若哈希不等，逐字段深比较并定位首个差异；不得只比较数量、长度、前几个名字或滚动哈希。
- **子进程替代：** 若无法直接在 Node 线程加载 TypeScript Worker 入口，改用子进程/独立进程时必须明确标注为降级覆盖，不能仍称“四方原定义通过”。
- **失败不掩盖：** 不允许用投影、删字段、只比子集的方式让比较通过。

### 11.5 性能测量

- 窗口期内不对被检页做 `Runtime.evaluate`；活性用心跳脚本。
- 目标识别用钩子（scriptId、URL 哈希前缀、提交计数、时间戳）。
- 长任务以面板内 `longtask` 为主，CDP 往返只作旁证。
- 测量前登记 D8 阈值；D8 未批准则阶段四不能关闭性能验收（可做技术测量，但不得记为通过）。
- 修复前后使用相同启动参数、相同窗口规则；不同口径的数字不得相除，改善倍率记 `n/a`。
- 结果导出在窗口结束后进行；导出不是窗口的一部分。

| 字段 | 说明 |
|---|---|
| 路径集合 | 文件与目录；大小写折叠键；无新增/删除/改名 |
| 大小 | 字节数 |
| 内容哈希 | 两套独立实现（PowerShell / Node）；逐文件一致 |
| 修改时间、创建时间 | 100 纳秒原值 |
| 属性 | 原始位值 |
| 文件 ID、链接数 | 句柄查询 |
| 变更时间 | 句柄查询 |
| USN | 只读查询 |
| 安全描述符 | 属主/属组/DACL 的 SDDL 哈希 |
| 备用数据流（ADS） | 每个流的名称 + **内容哈希**；见 13.2 |
| 最后访问时间 | 记录但不参与判定 |

### 13.2 ADS 的强/弱声明

- 只有对每个 ADS 的**内容**计算哈希，才能声明“ADS 未变”。
- 只比较名称和大小不构成内容证明。
- 若某些流无法读取：标记 `ADS-UNVERIFIED`，并缩小声明范围为“主数据流与可读流未变”，不得写“绝对未修改”。

### 13.3 判定

| 结果 | 条件 |
|---|---|
| `unchanged` | 路径、内容、元数据、ADS（或已缩小声明）、USN、变更时间、SDDL 全部满足 |
| `changed` | 路径/内容/元数据任一不满足；停止并报告 |
| `cannot-determine` | 仅绊线差异，且无法归因；记录 `source-unknown`，不判为未变化 |

### 13.4 不归因原则

- 不得从“设计上不访问”推断“变化必由外部主体造成”。
- 出现无法解释的变化：记录 `source-unknown`，停止，保留证据；不写“Codex 改的”“用户改的”或任何具体主体。
- 归因只能来自启动器日志、命令记录或用户书面确认。

### 13.5 阳性对照

检测工具必须先在假目录树上证明能发现：

- 内容变化（大小不变/改变）、新增、删除、改名、仅大小写改名。
- 相同内容重写（只 USN 变化）。
- 只改时间/属性/ACL。
- 删除后重建（文件 ID 变化）。
- 空目录增删。
- ADS 增加、硬链接增加。
- 只读对照组：零差异。

检测工具未通过阳性对照，不得用于原项目。

### 13.6 分范围结论

源（`src`/`scripts`/测试代码/配置）、完整 `dist`、历史证据三组分别给结论；每组有自己的摘要与逐文件清单。不能用一个总哈希代替分范围结论。

## 十四、安全指标（不得降低）

| 指标 | 定义 | 判定 |
|---|---|---|
| False Replacement | 不应替换却被替换的调用点数 | 必须 = 0 |
| Source Integrity | 原始脚本 SHA-256 三处一致（reference/observed/捕获读取） | 必须 = 100% |
| Safe Rejection Rate | 应拒绝的组中被拒绝的比例 | 必须 = 100% |
| Precision（发生替换时） | 替换中正确的比例 | 必须 = 100% |
| 分母为 0 | 没有可拒绝组/没有替换 | 记 `n/a`，不记 100%，不自动通过 |
| 零替换 | 没有发生替换 | 不能据此宣称阶段安全通过；必须报告原因与证据 |
| 版本不一致 | 源码哈希不符 | 标记 `version-mismatch`；不做位置级比较；不计入通过 |
| 旧构建结果 | `dist` 摘要与源码输入不匹配 | 不得用于新源码验收 |

**回归出口：** 阶段六必须把上述指标逐条列入最终报告；没有数据的项写 `n/a` 并说明原因。
