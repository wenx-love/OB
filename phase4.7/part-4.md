
## 十一、决策事项 D1—D16

D1—D10 是原方案提出的，这里按五项展开；D11—D16 是本轮因三项新发现和隔离要求新增的。每一项的“是否需要批准”都回答“是”，区别在于为什么需要、不批准时怎么办。

**各项需要在哪个阶段之前有结论：** 阶段零之前是 D12、D14、D15；阶段三之前是 D1、D2、D11、D13、D16；阶段一之前是 D3 和 D4 的规则；阶段二之前是 D5、D6、D7、D10；阶段四之前是 D8、D9。

### D1：Worker 输出格式

- **原始问题：** `vite.config.ts` 把 Worker 配置写在 `build.worker` 下，Vite 6.4.5 不读这个位置，实际输出是默认的 IIFE；源码里的构造参数却是 `{ type: 'module' }`。目前能运行，属于碰巧兼容。
- **推荐方案：** 候选 A 是顶层 `worker.format: 'es'` 配 module 构造；候选 B 是 `format: 'iife'` 配 classic 构造。两者各在工作副本里构建到独立目录并真机加载，按证据定案。默认选 A；A 有任一验收项不过就用 B。
- **理由：** A 让配置、源码声明和产物三者一致，同一批 Babel 依赖在主构建里已经以 ES 模块运行。B 是唯一已经被真机证明能加载的形态，适合作退路。
- **风险：** A 可能把 Worker 拆成多个文件，需要确认扩展环境下模块 Worker 能加载这些文件（unverified）。B 需要改一行产品源码的构造参数；IIFE 输出遇到依赖图里的动态 `import` 时的行为没有验证过。无论选哪个，`dist` 的文件名和哈希都会变。
- **是否需要批准：** 是。改构建配置和一行产品源码。需要批准的是“默认 A、不过则 B”这条规则，以及最终定案。

### D2：构建戳的位置

- **原始问题：** 没有任何机制能证明 `dist` 是由当前源码构建的。上一轮的全部“修复后”真机证据都跑在一份早于最终源码的构建上，事后才发现。
- **推荐方案：** 在 `dist` 里写一个构建戳文件，随扩展包走。内容是输入文件的哈希清单、产物文件的哈希清单、Vite 与 Rollup 版本、Worker 产物名与格式，不含时间戳。真机脚本启动前读取并比对，不符就拒绝运行。备选是把戳放在项目根目录、不进扩展包。
- **理由：** 放在 `dist` 里，戳和产物不会分离，装载的那份扩展自己就能说明来历。不含时间戳才能保证两次构建逐字节相同。
- **风险：** 扩展包里多一个文件。戳只能证明构建时刻的对应关系，构建之后手工改 `dist` 要靠产物哈希清单和校验脚本发现。
- **是否需要批准：** 是。它改变发布包的内容。不批准放进 `dist` 时用备选位置。

### D3：队列满的处理

- **原始问题：** 客户端队列上限 64，超出的任务被判为终态失败并写入缓存，不强制刷新就不会再分析。上一轮 run2 里面板的脚本总数第一次变化就是 65，最后是 477，这与“前 64 个被接受、其余 413 个因队列满被拒绝”相符。这是从计数推出来的（suspected），当时没有逐个读取脚本的状态。
- **推荐方案：** 队列满时客户端返回明确的“未受理”，不算失败、不进缓存。协调器把脚本标为“延后”，队列腾出位置时按发现顺序自动补投，界面上显示延后数量。备选是取消上限。
- **理由：** 脚本源码本来就全部留在面板内存里，延后不增加内存占用；保留一个有界的队列更容易推理和测试。
- **风险：** 页面持续产生新脚本时，延后列表会一直增长，需要显示数量并在超过阈值时提示。按发现顺序先到先服务，目标脚本可能排在大量小脚本后面，等待时间由阶段四实测。现有“队列上限，36 个失败”的用例预期要改，这是语义变更。
- **是否需要批准：** 是。改产品行为和一条既有测试的预期。

### D4：超时规则

- **原始问题：** 10 分钟的超时依据的是主线程的 145 秒。Worker 里先后分析 hpailist-2 和 512 KB 脚本，页面内计时合计 439 秒（两个脚本各自的耗时当时没有分开记录）。正常的长分析有可能被当成挂死而终止。
- **推荐方案：** 测量之前先登记规则：超时取“30 分钟”与“参考输入上实测的最大单脚本 Worker 耗时的 6 倍”两者中较大的一个。阶段一写入 30 分钟作为暂定值，阶段四实测后在该阶段出口定终值。
- **理由：** 超时的用途是发现挂死，不是限制性能。规则先于测量登记，数值就不能照着结果凑。
- **风险：** 真正挂死时至少 30 分钟才被发现；并发度为 1，这段时间里后面的脚本全部等待，所以必须同时有“分析中”和已用时间的显示（D5）。倍数和下限是经验取值；参考机器不等于用户的机器。
- **是否需要批准：** 是。需要批准的是规则本身。

### D5：面板进度显示与日志格式

- **原始问题：** 修复后有源码的脚本在发现时不再刷新计数，队列忙的时候数字停住；没有“分析中”和“失败”的计数；完成和失败的日志行不带脚本标识。上一轮承诺的“能显示分析进度和失败原因”没有做到，这也是性能判据误判的直接条件。
- **推荐方案：** 面板新增“分析中”“失败”两个计数（D3 获批时再加“延后”）；发现脚本时立即刷新计数；完成和失败的日志行在**末尾**追加脚本标识，原有前缀保持不变。
- **理由：** 这是让进度和失败可见的最小改动。保留前缀是为了不破坏按前缀解析日志的旧测试和脚本。
- **风险：** 要改 `panel.html`；读面板 DOM 的布局检查脚本需要复核；依赖“发现”和“完成”两行相邻配对的旧脚本在异步之后会配对错位，与是否追加标识无关，这些脚本已列入禁用清单。
- **是否需要批准：** 是。这是可见的界面改动。

### D6：后台对已清空脚本的守卫

- **原始问题：** `background.ts:228-239` 在异步取到源码之后才发 `script-discovered`，不检查该脚本是否仍属于当前文档；面板收到后会取消这个 scriptId 的退休标记（`panel.ts:1205`）。状态是 suspected，没有复现过。
- **推荐方案：** 先写一个能复现的测试。复现成立，才在后台加一行守卫：收集器里已经没有这个脚本对象时不外发。复现不成立，就不改 `background.ts`，这一项维持 suspected。
- **理由：** `background.ts` 紧邻捕获流水线，不应该凭猜测改它。
- **风险：** 面板一侧无法区分“迟到的旧脚本”和“新脚本”，所以阶段二的提交校验挡不住这种情况；如果不加守卫又确实存在这个问题，旧文档的脚本会被当作当前脚本分析并显示。守卫如果写错，会丢掉合法脚本。
- **是否需要批准：** 是。涉及 `background.ts`；复现结果出来后再请用户裁定。

### D7：捕获目标的筛选与提示

- **原始问题：** `startRuntimeCapture` 遍历全部候选时不看脚本是否已退休，页面重置后旧文档的候选可能被当成断点目标发给引擎（引擎拿到失效 scriptId 的后果 unverified）。这个问题在 Worker 改动之前就有。另外，分析改成异步之后，用户可能在目标脚本还没分析完时就点开始捕获，得到一次不完整的捕获而没有任何提示。
- **推荐方案：** 构造目标时跳过退休脚本的候选，并在“未纳入捕获”的提示里列出；还有脚本在分析或延后时，在提示里写明数量。不阻止开始捕获。
- **理由：** 验证路径和手动模式已经按“退休脚本不参与”处理，这里只是对齐。它只减少已失效文档的目标，不改引擎、不改捕获时机。
- **风险：** 必须用测试证明“没有退休脚本时目标清单逐字节不变”。只提示不阻止，用户仍可能得到不完整的捕获；改成阻止会改变捕获时机，超出本轮范围。
- **是否需要批准：** 是。它改变发给捕获引擎的目标集合。

### D8：主线程长任务阈值

- **原始问题：** 上一轮没有事先登记的验收线，拿 300 秒窗口和 10 秒窗口的数字做了对比。
- **推荐方案：** 从导航到目标脚本提交并渲染完成的整个窗口内，面板主线程的单个长任务低于 500 ms；所有 50 ms 以上的长任务逐条列出。测量前登记，测量后不改。
- **理由：** 修复前是 150 000 到 210 000 ms 的单次阻塞；上一轮修复后的构建在导航后头 10 秒里记录到的最长任务是 250 ms。500 ms 留有余量，又足以说明阻塞已消除。
- **风险：** 结果落地阶段（约 2.4 MB 的结果反序列化、983 个候选、约 1000 张卡片渲染）从未被测量过，有可能超过 500 ms。超过就按登记的标准判失败；是否另做渲染优化是单独的一项，需要另行批准。后台或被遮挡窗口的计时器节流会干扰长任务观测。
- **是否需要批准：** 是。阈值由用户定。

### D9：L1 运行器的完成闸门

- **原始问题：** `scripts/p47-l1-ob-run.ts:504-522` 的 `analysisSettle` 用的是同一种“计数稳定”判据。在 Worker 构建下，它可能在目标脚本还在分析时就放行，随后在断点覆盖闸门被拦下，而那时一次页面加载的预算已经花掉。
- **推荐方案：** 把这个闸门改成按目标脚本判定（经 D10 的钩子），等待上限按阶段四的实测重新设定，同步更新结构测试。不运行 L1。
- **理由：** 它与性能脚本的判据同源，现在一起改，可以避免下一次 L1 白白消耗预算。
- **风险：** 不运行 L1 就无法端到端验证这次改动，证据只有结构测试和本机页面上的演练。它把 D10 的钩子带进了 L1 路径。运行器写入 L1 证据目录的方式不在这次改动范围内。
- **是否需要批准：** 是。不批准时，把它记为“下一次 L1 之前必须完成的前置条件”。

### D10：面板只读测试钩子

- **原始问题：** 面板的分析状态是模块私有的，DOM 只有全局计数，从外部无法知道某个脚本的结果是否已经提交。性能判据的缺陷根源在这里。
- **推荐方案：** 在面板页上挂一个只读对象，提供页面纪元、逐脚本的状态快照、客户端队列统计、按 scriptId 取已提交结果。全部返回副本，没有任何写操作。先例是后台已有的 `__obRecoverTest`。
- **理由：** 没有它，只能回到依赖 DOM 计数和日志的间接判据，而那正是上一轮出错的地方。
- **风险：** 发布包里多一个调试入口（只能从扩展页上下文访问）；测试有可能因此依赖内部结构。
- **是否需要批准：** 是。属于产品代码改动。不批准时，G4-1 无法按现在的定义满足，完成判据需要重新设计。

### D11（新增）：L2/L3 落盘默认只校验

- **原始问题：** 一次普通的 `vitest run` 可以静默覆盖 47 个历史验收文件，而测试回读的是刚写进去的内容，所以自己还会通过（2.4、8.2）。
- **推荐方案：** 默认只比较“将要写入的内容”与“已归档的内容”，不一致或文件缺失就让测试失败并给出差异，不写任何文件。只有通过环境变量显式给出一个位于项目树之外的输出目录时才写；给的目录在项目树内就拒绝。辅助函数返回实际使用的目录，测试的回读跟着走。
- **理由：** 这样历史证据就成了回归基准，流水线输出一旦变化，测试会失败而不是悄悄改掉证据。
- **风险：** 改的是产生证据的测试辅助代码，最容易在不经意间削弱断言，所以配了断言保持检查。以后流水线输出需要有意变更时，必须走一次显式的、经批准的重新生成。全新检出、缺少归档文件时测试会失败，这是预期行为。
- **是否需要批准：** 是。不批准时退回“只检测”：每次 Vitest 之后核对 63 个文件，有变化即停止。

### D12（新增）：工作副本模式与一次性提升

- **原始问题：** 原项目没有版本库；工具在原地运行会自己写文件；还有另一个主体对它有写权限。
- **推荐方案：** 阶段零到阶段六全部在工作副本里进行，原项目只在阶段六之后的提升闸门里变化一次。备选是每个阶段批准后各提升一次。
- **理由：** 一次性提升让“原项目未变化”对每个阶段都可证明，审查的是一份完整的变更集，中途任何阶段失败都不留痕迹。
- **风险：** 原项目会在更长时间里保持现在这个已知有缺陷的状态。提升是一次较大的写入，而且按设计不在原项目里重跑测试。提升之前 Codex 在原项目里看不到改动，审查依赖审查包（D14）。
- **是否需要批准：** 是。它决定了所有阶段的执行方式。

### D13（新增）：工作副本使用版本库

- **原始问题：** 没有版本控制时，阶段之间的差异和回滚只能靠清单和整树归档，可行但笨重。此前有一轮明确禁止创建 Git 提交。
- **推荐方案：** 只在工作副本上使用 Git，元数据目录放在工作副本之外，跟踪源码、测试、脚本、文档和配置，不跟踪 `node_modules`、`dist` 和证据目录。标签依次是原样副本、路径中和之后、每个阶段的出口。原项目永远不初始化为版本库。本机已有 Git 2.55。备选是每个阶段出口存一份整树归档加清单。
- **理由：** 标签能给出精确的差异和可核对的回滚点。
- **风险：** Git 的换行转换之类的行为可能改动工作副本里的字节，所以必须关闭自动换行转换，并在每次检出后用清单核对。清单仍是判定依据，Git 只是便利工具。
- **是否需要批准：** 是。它重新界定了此前“不创建 Git 提交”那条禁令的适用范围，需要用户明确同意；不同意就用备选。

### D14（新增）：运行根目录的位置与权限、归档副本、审查包的位置

- **原始问题：** 原方案把各阶段的备份放在 `C:\Users\Administrator\TEMP\opencode` 下，本文新设的运行根目录默认也在这里。本轮查明这个目录上有给 Codex 沙箱组的显式“修改”权限，并继承到所有子项（2.9）。照原样做，工作副本、基线清单、整树归档和检测工具都可以被别人改动。另外，TEMP 可能被清理，只有一份归档就是单点。
- **推荐方案：**
  - 运行根目录仍用 `C:\Users\Administrator\TEMP\opencode\p47r\<运行编号>`，但建立时关闭它的继承：我自己的账户和 SYSTEM 完全控制，Codex 沙箱组只读，不给其他账户权限。设置前后各读一次访问控制列表并记入阶段记录。
  - 归档和每份基线清单的 SHA-256 在生成的当时写进回复，以回复为准。
  - 基线归档和清单在另一个卷上由用户指定的位置再存一份。
  - 可选：在 D 盘建一个空的假目录树，让检测工具在与原项目相同的卷上自测。`D:\Projects` 下新建的目录会继承“Authenticated Users = 修改”，所以它也要做同样的权限限制。
  - 审查包放在运行根目录的 `review` 子目录里（沙箱组只读），或放到用户另行指定的位置。
- **理由：** TEMP 下的位置是这个环境里已经获准的外部写入位置。基线不能放在别人改得动的地方，否则“与基线比对”没有意义。给审查方只读而不是完全不给，是为了让 Codex 能独立复核全部材料。
- **风险：** 设置权限属于权限改动，虽然对象只是我新建的目录，仍然需要用户明确批准。设置错了，可能让 Codex 读不到，也可能仍然留着写权限，所以设置后要读回核对，并请用户或 Codex 从他们那一侧实测能否读取。我无法从沙箱账户的视角测试。沙箱账户能否穿过 `C:\Users\Administrator` 走到 TEMP，本轮没有验证（2.9）。
- **是否需要批准：** 是。涉及写入位置和权限设置。不批准设置权限时的退路：把整个运行根目录当作不可信位置，每次使用基线和工具之前都与回复里公布的哈希核对；工作副本一直在变，没有固定的哈希可比，它被别人改动只能靠 GU-4 事后发现。

### D15（新增）：静默窗口与可选的提权日志导出

- **原始问题：** 原项目和运行根目录所在的 TEMP 上都有其他能写入的主体（2.1、2.9）；非管理员会话读不到变更日志的原因码，也看不到其他账户的进程；绊线被触发而无法归因时，只能判为“不能判定为未变化”。
- **推荐方案：** 用户和 Codex 对每个阶段约定静默窗口。可选：用户在管理员窗口里做一次只读的日志导出（6.7）。
- **理由：** 技术手段只能约束我自己的进程，其余只能事后发现；约定是补上这段空缺的唯一办法。
- **风险：** 依赖各方遵守。提权导出需要用户亲自操作，导出的是整个卷的记录，交出前应当按项目的文件 ID 过滤。变更日志记录的是“哪个文件、什么时候、什么类型的变化”，不记录是哪个账户或进程做的。日志有容量上限，旧记录会被循环覆盖：如果想用它查清 11-10 22:48 那两次事件的类型，需要尽早导出，不必等到阶段零。项目在 D 盘，TEMP 在 C 盘，两个卷各有各的日志，要分别导出；本轮只查过 D 盘的日志范围。
- **是否需要批准：** 是。这是需要用户和 Codex 双方作出的承诺。

### D16（新增）：真机脚本的路径约定与新证据的存放

- **原始问题：** 脚本把根目录、输出目录、profile 路径写死；新证据会以固定文件名落在 `test/acceptance` 里，与历史证据混在一起（2.5、8.3）。
- **推荐方案：** 本次整改要运行的脚本改用一个公共路径模块：项目根由脚本自身位置推出；输出目录和 profile 根目录必须显式给出，没有默认值；落在项目证据目录内就拒绝；端口取自登记区间；输出独占创建。新证据放 `<run>\evidence`，是否收进项目在提升时决定，并且只以新目录、新文件名的形式。其余旧脚本不改造，在工作副本里中和，并且不运行。
- **理由：** 只改要用的脚本，改动面最小；没有默认路径，就不存在“忘了设置而写进证据目录”的可能。
- **风险：** 改造后的脚本不设环境变量就拒绝运行，习惯直接运行的人会碰到。新旧两种约定并存是维护负担；把 48 个脚本全部迁移不在本轮范围内。
- **是否需要批准：** 是。它改变证据的产生和存放方式。
