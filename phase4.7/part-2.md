
## 四、执行模型与隔离方案

### 4.1 总原则

**从阶段零到阶段六，原项目目录只被读取，不被写入，也不作为任何工具的工作目录、配置位置或路径参数。** 全部修改、测试、构建和真机运行都在一份隔离的工作副本里进行。原项目只在阶段六通过之后、经用户和 Codex 单独批准的“提升闸门 P”里发生一次变化（见 10.8）。

这样做的理由：

- 原项目里已有的工具行为会自己写文件（2.2、2.3、2.4），在原地运行就无法保证不变。
- 原项目没有版本库，一旦被改，只能靠备份还原。
- 这也让“证明没有变化”对每个阶段都成立，而不只是阶段零。

### 4.2 运行根目录的布局

所有产物放在一个运行根目录下，位置由决策 D14 确定，默认是 `C:\Users\Administrator\TEMP\opencode\p47r\<运行编号>\`（下文写作 `<run>`）。它在原项目之外。

**运行根目录的权限。** 这个 TEMP 目录按当前权限可以被 Codex 沙箱组修改（2.9），新建的子目录会继承这一点。所以推荐在建立 `<run>` 时关闭它的继承：只给我自己的账户和 SYSTEM 完全控制，给 Codex 沙箱组只读。这样审查方能读到全部材料，但改不了。这是对一个新建目录设置权限，不涉及原项目，但仍然是权限改动，需要用户批准（D14）。不批准时，把整个 `<run>` 当作不可信位置对待：每次使用基线和工具之前，先与交付回复里公布过的哈希核对；工作副本本身一直在变，没有固定的哈希可比，它被别人改动只能靠 GU-4（每一处差异都要有出处）事后发现。

```text
<run>\
  baseline\    原项目的基线清单、整树归档（只读保存）、修复前 dist 的固定副本
  controls\    检测工具的自测用假目录树
  tools\       清单、比对、复制、守卫、启动器等工具，以及各自的哈希
  sandbox\     工作副本：全部编辑、测试、构建都在这里
  gitdir\      工作副本的版本库元数据（若 D13 获批），放在 sandbox 之外
  out\         每个阶段的命令日志、标准输出、守卫日志、清单与差异
  evidence\    新产生的真机证据：独占创建、追加式索引
  profiles\    浏览器 profile：一次运行一个，不复用
  tmp\         子进程的 TEMP/TMP，以及 npm 缓存
  review\      交给用户和 Codex 审查的阶段包（位置可由 D14 另行指定）
```

- **路径长度：** 原项目最长相对路径是 120 个字符。运行根目录名保持简短，复制工具会检查每个目标路径并在超过 240 个字符时拒绝。
- **保留策略：** 运行根目录里的任何东西，未经批准不删除；失败的运行记录永不删除。profile 例外：每次真机运行结束后删除，删除前记录文件数和字节数。
- **容量：** 一份归档和一份工作副本各约 100 MB（都含 `node_modules`），每个 profile 约 50 到 200 MB。C 盘可用 81 GB，D 盘可用 386 GB。

### 4.3 六层隔离

没有哪一层单独可靠，所以分层设置，并写明每一层防不住什么。

| 层 | 做法 | 防住什么 | 防不住什么 |
|---|---|---|---|
| L0 位置隔离 | 工作目录、配置文件、工具入口全部位于 `<run>\sandbox`；原项目路径不出现在任何命令行里 | 靠相对路径、`__dirname`、`import.meta.url`、`projectRoot()` 定位的写入（Vitest 缓存、Vite 临时文件、`closeBundle` 复制、`persistRun`） | 源码里写死的绝对路径 |
| L1 路径中和 | 把工作副本里**代码文件**中的原项目根路径和固定 TEMP 路径机械替换成 `<run>` 下的路径，逐文件记录 | 旧脚本被误运行时写原项目、删公用 profile | 运行时拼出来的路径；不在替换范围内的文件 |
| L2 启动器 | 所有命令经一个启动器执行：按阶段的命令白名单、参数与环境检查、完整日志 | 临时起意的命令、带错参数、用 `npx` 触发的额外写入、误跑证据生成脚本和 L1 运行器 | 绕过启动器手工执行的命令 |
| L3 写入守卫 | 给 Node 进程预加载一个文件系统守卫：写入目标不在允许目录内就拒绝并记录 | Node 进程内经 `fs` 的越界写入，包括 Vitest 的工作进程 | 非 Node 进程（Chrome、esbuild 的原生进程、`cmd`、`git`）；不经 `fs` 的写入 |
| L4 输出分离 | 新证据只写 `<run>\evidence`，独占创建；新脚本不带任何默认输出路径 | 新运行覆盖历史证据 | 没有改造的旧脚本（它们被 L2 禁止运行） |
| L5 事后检测 | 每批命令之后对原项目做一次清单比对；阶段首尾做完整比对 | 前面各层的任何漏网 | 它只能发现，不能阻止 |

另有一项不属于技术手段的约定：**静默窗口**（6.6）。原项目和 TEMP 目录上都有其他能写入的主体（2.1、2.9），技术隔离只能管住我自己的进程。

### 4.4 L1 路径中和的细则

- **范围：** `scripts/` 下全部 48 个文件，加项目根目录的 10 个零散代码文件（`.ts`、`.cjs`、`.mjs`、`.js`）。
- **明确不碰：** `docs/`、`test/acceptance/`、`test/fixtures/`、根目录的 3 个日志文件、`test-pages/` 下的 2 个说明文档、`dist/`、`node_modules/`。这些文件里的路径是历史记录，改了就是改证据。
- **映射规则：** 原项目根的正斜杠和反斜杠两种写法都替换为 `<run>/sandbox`；`C:/Users/Administrator/TEMP/opencode/` 前缀替换为 `<run>/profiles/legacy/`。不替换 Chrome 可执行文件的路径（那是只读的公用程序）。
- **记录：** 生成一份中和清单，逐文件写明替换前哈希、替换后哈希、每种映射的替换次数。
- **残留检查：** 替换后在上述范围内搜索原项目根（各种写法）和未替换的 TEMP 字面量，命中数必须为 0。
- **等价性检查：** 中和之前先在原样副本上跑一次 `tsc` 和 Vitest，中和之后再跑一次，两次结果必须逐条相同（见 10.1 的 G0-6）。测试只读取脚本源码做结构断言，不执行脚本，所以这一步能发现中和是否改变了任何断言结果。
- **提升时的还原：** 中和属于工作副本专用的改动，不进入原项目。提升时对每个被中和过的文件做逆映射，并做往返校验：把提升内容再中和一遍，必须与工作副本里的内容逐字节相同。

### 4.5 L2 启动器的细则

- **输入：** 阶段编号加命令编号，不接受自由拼写的命令行。每个阶段的白名单在该阶段开工前随方案一起登记。
- **环境：** 工作目录固定为 `<run>\sandbox`；`TEMP`、`TMP`、`npm_config_cache` 指到 `<run>\tmp`；`NODE_OPTIONS` 由启动器整体设定为“预加载写入守卫”，覆盖外部已有的值并在日志里记下原值。
- **工具入口：** 直接用 `node` 调用工作副本里的入口文件（`node_modules\typescript\bin\tsc`、`node_modules\vitest\vitest.mjs`、`node_modules\vite\bin\vite.js`），不用 `npx`。
- **拒绝条件：**
  - 任一参数或环境变量的值含有原项目根路径（正反斜杠、大小写、`file:///` 形式、`\\?\` 前缀都算）。
  - `--config`、`--root`、`--dir`、`--outDir`、`--outputFile` 解析后不在 `<run>` 之内。
  - `tsc` 不带 `--noEmit`。
  - 目标脚本在“旧脚本禁用清单”“证据生成脚本禁用清单”里，或是 `p47-l1-ob-run.ts`。
  - 系统里存在指向原项目的 `subst` 映射，或 `<run>` 内存在解析到原项目的联接点。
- **日志：** 每次调用记录命令编号、完整参数、工作目录、环境摘要、起止时间、退出码、标准输出与错误输出文件的哈希。
- **限制：** 8.3 短路径名之类的别名靠字符串检查发现不了，由 L3 的真实路径解析和 L5 的事后检测兜底。

### 4.6 L3 写入守卫的细则

- **加载方式：** 一个 CommonJS 预加载模块，包装 `fs` 和 `fs.promises` 的写类函数（写文件、追加、写流、以写方式打开、复制与硬链接的目标、重命名的两端、删除、建目录、截断、改权限、改时间戳、建符号链接），包装后调用 `syncBuiltinESMExports()`，让 ES 模块的具名导入也拿到包装后的函数。
- **判定：** 把目标解析成真实路径（目标不存在时取最近的已存在上级目录的真实路径，再拼回剩余部分）。在允许目录内就放行并记日志；否则抛出明确的错误并记日志。允许目录按命令类别给出，并且永远只在 `<run>` 之内。测试、构建和真机脚本的允许目录是：`<run>\sandbox`、`<run>\out`、`<run>\evidence`、`<run>\profiles`、`<run>\tmp`、`<run>\gitdir`、`<run>\controls`。出审查包的命令另加 `<run>\review`（或 D14 指定的位置）。`<run>\baseline` 写完之后对所有命令只读。
- **对原项目的读取：** 测试、构建和真机脚本读取原项目也会被拒绝并记录。工作副本里的任何东西都不应该需要读原项目；出现读取就说明有硬编码路径漏网。
- **清单与归档工具是例外，因为它们必须读原项目：** 这类工具只有三种（清单、归档、比对），代码量小，随审查包提交；它们只用读权限打开原项目里的文件，先在假目录树上自测，再用于原项目。它们有一部分用 PowerShell 写，不在 Node 守卫的覆盖范围内，所以“它们没有写原项目”靠的是代码审查、自测和首尾清单比对，而不是守卫。
- **自测不碰原项目：** 守卫的“禁止目录”由环境变量传入。自测时把它设成 `<run>\controls` 下的一个假目录，再做三项探针：写禁止目录必须被拒；写允许目录必须成功；读禁止目录必须被拒。这样即使守卫有缺陷，探针也碰不到原项目。
- **确认守卫在 Vitest 的工作进程里生效：** 用一个只存在于工作副本的探针测试读取守卫设置的全局标记。预加载能否被 Vitest 3.2.7 的工作进程继承属于 unverified；如果探针显示没有继承，改用一个只存在于工作副本的包装配置把守卫挂到 `setupFiles` 上，并作为偏差登记。
- **写明的限制：** 守卫只覆盖 Node 进程里经过 `fs` 的调用。Chrome、原生的 esbuild 进程、`cmd`、`git`、PowerShell 不受它约束，这些由 L0、L1、L2、L5 负责。守卫是绊线，不是安全边界。

### 4.7 不采用的做法

- **给原项目加“拒绝写入”的访问控制项，或设只读属性：** 这会改动原项目每个文件的安全描述符或属性，本身就是对原项目的修改，还会影响 Codex 沙箱的访问。如果用户想要这层硬保护，可以自己操作，并在基线清单之前完成。
- **用联接点或虚拟盘符把原路径指到副本：** 需要改动原项目的位置或名字。
- **依赖卷影副本：** 需要管理员权限，本轮会话没有。

## 六、如何证明原项目源码、完整 dist 和历史证据没有变化

### 6.1 比对对象

对原项目整棵树的每个文件和每个目录各记一行，**包含 `node_modules`**（2.3 说明了为什么必须包含）。在每个阶段的入口和出口各做一份完整清单；每批命令之后做一份快速清单。

| 字段 | 取法 | 作用 |
|---|---|---|
| 相对路径 | 原样记录，另记一个大小写折叠后的键用来发现仅大小写不同的重名 | 路径集合 |
| 类型 | 文件或目录 | 路径集合 |
| 大小 | 字节数 | 内容 |
| 内容 SHA-256 | 两套独立实现各算一次：PowerShell `Get-FileHash` 和 Node `node:crypto`，必须一致 | 内容；同时防工具自身出错 |
| 修改时间、创建时间 | 100 纳秒精度的原始值 | 元数据 |
| 属性 | 原始位值 | 元数据 |
| 文件 ID、链接数、卷序列号 | 句柄查询 | 发现“删除后重建”“被替换成另一个文件” |
| 备用数据流列表 | 名称与大小 | 发现藏在主数据流之外的内容（本轮没有检查过现状，unverified） |
| 变更时间 | 句柄查询 | 绊线：任何元数据或内容变化 |
| USN | `fsutil usn readdata`（只读子命令） | 绊线：包括相同内容的重写 |
| 安全描述符 | 属主、属组、访问控制列表的 SDDL 文本及其哈希 | 绊线：权限变化 |
| 最后访问时间 | 记录，但不参与判定 | 见 6.3 |

每份清单另记：卷序列号、变更日志的 ID 和当前位置（`fsutil usn queryjournal`）、项目根的访问控制列表、当时的进程快照、所用工具各自的哈希。

**关于原生辅助程序：** 读取变更时间和文件 ID 需要调用系统接口。本轮我自己的第一版辅助程序就有结构体对齐错误（第三节第 4 条）。因此规定每个辅助程序必须带自检（结构体大小断言），并把它读到的大小和修改时间与 `Get-Item` 逐项交叉核对，全部一致才允许用于原项目。

### 6.2 判定标准

**硬性条件（任一不满足即判“已变化”）：**

1. 文件集合与目录集合完全相同：没有新增、删除、改名，大小写折叠后也没有冲突。
2. 每个文件的 SHA-256 和大小相同，且两套哈希实现一致。
3. 每一项的修改时间、创建时间、属性相同。
4. 每一项的文件 ID、链接数相同。
5. 每个文件的备用数据流列表相同。

**绊线（出现差异不直接判失败，但必须逐项归因）：**

6. 每一项的 USN 相同。
7. 每一项的变更时间相同。
8. 每一项的安全描述符相同。
9. 变更日志的 ID 相同（ID 变了说明日志被重建，USN 失去可比性）。

**判定结果只有三种：**

- **未变化：** 1 到 9 全部满足。
- **已变化：** 1 到 5 有任一条不满足。立即停止，保留现场，报告差异。不自动还原，因为还原也是对原项目的写入，需要单独批准。
- **不能判定为未变化：** 1 到 5 全部满足，但 6 到 9 有差异。这说明有主体触碰过原项目的元数据，或以相同内容重写过文件。按设计，我方的任何命令都不以原项目为目标，所以这类差异不可能归因到启动器日志里的命令。处理方式是：如实写成“内容未变，但被外部触碰”，列出受影响的条目，由用户裁定是否接受；阶段门槛在裁定前保持未通过。

不允许把第三种结果写成第一种。

**分范围给出结论。** 清单覆盖整棵树，但结论按下表的每一行分别给出，每一行都要单独满足上面的条件。规划时刻各范围的目录摘要如下（算法和完整值见附录 B.1），阶段零的基线必须先与它们对上：

### 6.3 明确排除的字段及原因

**最后访问时间不参与判定。** 做清单需要读取原项目的每个文件，读取可能更新最后访问时间（本机设置是“系统管理，启用更新”）。这是只读核对不可避免的、已知且有界的副作用，在这里事先声明。读取不改内容和修改时间；读取不改变 USN、变更时间和文件 ID，这一点本轮已经在原项目的真实目录树上观测到（2.8）。阶段零仍会在假目录树上再做一次专门的验证，因为本轮的观测只覆盖 D 盘这一个卷和本轮用到的几种读取方式。

### 6.4 检测工具必须先证明自己能发现变化

一个从不报错的检测工具没有证明力。阶段零的第一步是在 `<run>\controls` 的假目录树上植入下列每一类变化，逐类确认工具能发现并归到正确的类别：

- 内容变化（大小不变）、内容变化（大小改变）。
- 新增文件、删除文件、改名、仅大小写改名。
- **相同内容重写**（复制覆盖，保留修改时间）：必须只表现为 USN 变化，这正是 2.2 的情形。
- 只改修改时间；只改属性；只改访问控制列表。
- 删除后以相同内容重建（文件 ID 应当不同）。
- 新增与删除空目录。
- 增加备用数据流、增加硬链接。
- 对照组：只读取、只哈希，必须报告零差异。

阶段零里还有两项发生在工作副本上的对照。按 2.2 的判断，预期结果是：

- 在工作副本里跑 Vitest 之后，工具报告“`dist` 的 6 个静态文件 USN 变了、内容没变”。
- 用不带复制插件的配置再跑一次，工具报告这 6 个文件的 USN 没变。

两项都符合预期，就同时证明了检测工具有效和 2.2 的归因成立。任何一项不符合预期都如实记录：那说明 2.2 的归因有误或检测工具有问题，需要先查清再继续。

### 6.5 独立复核

为了不让结论只依赖我写的清单工具：

- **归档比对：** 阶段零把原项目打成一份 zip 归档，归档里每个条目的哈希与基线清单逐项比对。此后任何时候都可以把原项目与这份归档逐文件比对，不经过清单工具。
- **哈希在生成的当时公布：** 归档和每份基线清单一生成，它们的 SHA-256 就写进当时的回复里。运行根目录所在的位置别人也可能写得到（2.9），所以以回复里的记录为准，不以目录里的文件为准。
- **独立校验脚本：** 提供一个不超过百行的 Node 脚本，只做“遍历、哈希、与清单比对”，供用户或 Codex 自行运行。
- **附录 B 的清单：** 规划时刻的逐文件哈希和目录摘要已在本文给出，目录摘要的算法写明了，可以独立复算。

### 6.6 静默窗口约定

- **开窗前：** 用户确认在窗口期内不让 Codex、编辑器、同步或备份工具、其他会话触碰原项目，并把确认写进阶段记录。
- **两端各记一次：** 进程快照（命令行或工作目录含原项目路径的进程，以及所有 Chrome、Node 进程）；变更日志 ID 与当前位置；项目根的访问控制列表。
- **限制：** 非管理员会话只能看到当前用户可见的进程，看不到其他账户（例如 Codex 沙箱账户）的进程命令行。所以这一条主要靠约定，技术手段只能事后发现。
- **约定同样覆盖运行根目录。** 工作副本、工具和基线被别人改动，后果与原项目被改动一样严重。D14 的权限限制获批时，这一条由权限保证；没有获批时，靠每个阶段首尾与已公布的哈希核对。
- **窗口期内出现无法归因的差异：** 判为 6.2 的第三种结果，保留全部现场，停止，报告。查明原因并重新取基线之后才能重做该阶段。
- **两个阶段之间不在窗口期内。** 这段时间原项目可能被别人读取或触碰，本方案不阻止。每个阶段入口的完整清单要与上一阶段出口的清单比对：有差异就先报告，由用户裁定后才开工。内容层面的差异在查清并处理之前，不进入提升闸门。

### 6.7 可选的增强：一次提权的日志导出（D15）

非管理员只能读到每个文件“最后一条”日志记录的位置，读不到记录内容。如果用户愿意在管理员窗口里执行一次只读的日志导出（从阶段入口记下的位置读到出口），就能得到窗口期内**全部**记录及其原因码，包括“创建后又删除”这种不留文件的操作。把记录里的文件 ID 和上级目录 ID 与清单对照，可以直接证明“窗口期内原项目没有任何日志记录”。没有这一步时，瞬时文件只能靠目录的变更时间和 USN 间接发现。

两点限制：变更日志记录的是哪个文件在什么时候发生了哪一类变化，不记录是哪个账户或进程做的；日志的容量有上限，旧记录会被循环覆盖。11-10 22:48:38 项目那次事件的记录，本轮开始时还在 D 盘日志的有效范围内；TEMP 在 C 盘，那个卷的日志本轮没有查。想用日志确认这两次事件的类型，就要尽早导出。

### 7.3 十项保护措施

1. **原项目里不运行任何东西。** 这一条覆盖上表全部写入者。
2. **工作副本里的证据副本也必须保持逐字节不变。** 每批命令之后核对上表各组的目录摘要和逐文件 USN。
3. **把“证据副本被改写”当作回归信号，而不是可接受的副作用。** 如果在工作副本里跑 Vitest 导致 63 个落盘文件中任何一个被改写，说明流水线输出与归档的证据不一致。处理方式是停止、保留差异、报告，不接受“重新生成后测试通过”。
4. **把 L2/L3 测试的落盘改为默认只校验（D11）。** 默认情况下只比较“将要写入的内容”与“已归档的内容”，不一致就让测试失败并给出差异，不写任何文件。只有显式给出一个位于项目树之外的输出目录时才写，并且拒绝写进项目树。
5. **证据生成脚本列入禁用清单。** 上表里的脚本一律不在任何阶段的启动器白名单里。阶段二会改变面板日志的时序和格式，而这些脚本按旧格式解析日志，重新运行只会产生与历史证据不可比的新文件。
6. **L1 运行器三重拦截。** 启动器按文件名拒绝；路径中和之后，在工作副本里预置一个与它的输出同名的哨兵文件，使它自带的“输出已存在即拒绝”守卫在启动浏览器之前生效；每次阶段出口核对工作副本里的台账副本未变。哨兵文件名要随运行器的输出名同步，由启动器的预检负责。
7. **真机运行的网络隔离。** 所有真机脚本都带 `--host-resolver-rules=MAP * ~NOTFOUND , EXCLUDE 127.0.0.1`，并关闭 Chrome 的后台联网与组件更新。运行期间被动记录所有已附着页面的网络请求，出现任何非本机主机即判该次运行失败。限制：这条规则拦主机名，不拦直接写 IP 的地址；浏览器进程自身的后台流量不在页面级监听范围内。
8. **新证据与历史证据物理分开。** 新证据只写 `<run>\evidence`，文件名带阶段、用途和序号，独占创建，已存在即拒绝。每创建一个文件，就在一份追加式索引里记一行（路径、大小、哈希、创建时间、上一行的哈希），形成可校验的链。
9. **提升时把现有证据排除在外。** 提升清单里不允许出现基线里已有的证据文件和历史报告。需要更正的内容以新文件的形式增加。
10. **不清理。** 运行根目录内的内容未经批准不删除；失败的记录永不删除、不覆盖、不用重跑替代。
