### P0-1 的各问

- **生命周期：** `analyze` 入队，`pump` 取出置为 `inflight` 并启动计时器，`finish` 写缓存、结算、再 `pump`。
- **崩溃后 inflight：** 不释放，计时器也不清。
- **重建竞态：** JS 单线程，没有数据竞争。逻辑问题是崩溃后状态自相矛盾：`worker` 为空而 `inflight` 仍在，新 Worker 要等计时器触发才会建。
- **迟到的旧事件：** `onerror` 不校验 Worker 实例，若被触发会终止新 Worker 并清空队列。Chrome 在 `terminate()` 之后是否还会投递 `error` 属于 unverified。迟到的 `message` 有请求 id 把关，是安全的。
- **统一清理：** 没有。超时、崩溃、取消、销毁四条路径各写各的，只有崩溃路径不结算在飞行任务。
- **其他：** `messageerror` 没有处理；瞬时错误也会写缓存（:189、:209）；`onerror` 路径没有任何测试，`FakeWorker` 声明了 `onerror` 却从未触发。

### P0-2 的各问

- **刷新是否取消旧分析：** 不取消。
- **重复追加的三条路径：**
  - 初次分析未完成时刷新，两个请求各自通过身份检查、各追加一次。
  - 连点两次刷新，两个循环交错。
  - 刷新循环迭代的是活的 Map，会把刷新期间新发现的脚本再强制分析一遍。
- **新旧请求如何区分：** 无法区分。客户端缓存只按 scriptId，面板的续延不带请求标识。
- **是否需要代次：** 需要两级：页面纪元，和每个脚本的请求序号（只有最新请求可以提交）。
- **是否必须校验 scriptHash：** 面板内用源码字符串全等更强也更便宜。SHA-256 用来核对 Worker 回显和留证。`DiscoveredScript.hash` 只取前 1000 字符加长度（`script-collector.ts:126-134`），不能当身份用。
- **旧结果覆盖新结果：** 同一脚本对象的源码不变，两次结果内容相同，实际危害是重复和状态错乱。旧请求的瞬时错误晚到时会给已成功的脚本写上 `analysisError`（:1241），成功提交也不清旧错误。

### P0-3 的各问

- **重置时刷新循环：** 不会停。取消后循环继续，并在新 Worker 上发起新的强制分析。
- **旧脚本集合是否仍会提交：** 捕获激活时 Map 不清空，旧脚本对象仍通过身份检查，会被重新分析并提交。捕获未激活时 Map 被清空，但挂起的迭代器会继续遍历之后插入的新页脚本，造成新页候选重复。
- **退休脚本是否重新入队：** 会，经由刷新循环。
- **捕获是否使用旧页脚本：** `startRuntimeCapture` 遍历 `allCandidates` 时不查退休状态。引擎拿到旧 scriptId 后的实际后果属于 unverified。
- **页面身份检查：** 目前只有对象身份一项，没有纪元，也没有退休检查。

### P1-1 的各问

- **实际读取的层级：** 顶层 `worker`。当前写在 `build` 下的 `format` 和 `rollupOptions` 全部无效，生效的是默认值 `iife`。
- **产物位置：** `dist/assets/decoder-analysis.worker-CMwEr3ip.js`（1 647 698 字节，开头是 `(function() { "use strict"`）。命名来自 Vite 的默认 `assets/[name]-[hash].js`（`:40261-40272`）。
- **其他无效字段：** `assetFileNames: 'chunks/[name][extname]'` 对 Worker 产物不起作用，因为产物以显式文件名发出（`:40554-40557`）。它的注释写的是早已删除的 `getURL('chunks/…')` 方案。
- **URL 是否正确：** 正确。构建后是 `new URL("/assets/…", import.meta.url)`，在扩展页内解析为 `chrome-extension://<id>/assets/…`。
- **不一致之处：** 构造参数是 `{type:'module'}`，产物却是 IIFE。构建期这个参数不参与格式决定（`:41637-41639`）。目前能运行，但属于碰巧兼容。

### P1-2 的各问

- **为什么只看计数：** 面板没有按脚本暴露状态的途径。DOM 只有全局计数，卡片和完成日志都不带 scriptId（`panel.ts:1264`、`1301-1330`）。
- **为什么误判：** 修复后发现脚本时不再刷新计数（见追加发现 A5），队列被长任务占住时计数器恰好不动，于是“卡住”被判成“完成”。
- **污染来源：** 探针每 0.5 秒对被检页做一次 `Runtime.evaluate`，每次产生一个新脚本并进入分析队列。run2 里 471 次探针对应脚本总数 477。

## 四、整改方案

建议执行顺序为零、三、一、二、四、五、六（编号沿用你给的名称）。阶段三提前有三个理由：

- `dist` 已经过期，不先修构建，后面任何真机验证都跑在来历不明的产物上。
- Vitest 目前会写 `dist`。
- Worker 输出格式决定阶段一协议里哈希的实现方式。

每个阶段都遵守以下约定：

- **备份与清单：** 开工前全量备份到 TEMP 并记录哈希清单。
- **先红后绿：** 新测试先在当前代码上跑出失败并存档，再改代码使其通过。
- **保护文件：** 五个受保护模块加 `parser.ts`、`capture-plan.ts` 的哈希必须不变。
- **证据不可变：** 四份 raw-run、`registry.json`、台账必须不变。

### 阶段一：Worker 崩溃恢复与任务生命周期

1. **根因：** P0-1 各点，加 A3、A4 的超时依据。
2. **文件：**
   - `decoder-analysis-client.ts` 的 `analyze`、`attachToActive`、`pump`、`ensureWorker`、`onWorkerMessage`、`finish`、`breakWorker`、`drainQueueAsFailed`、`cancelAll`、`dispose`。
   - `decoder-analysis.worker.ts` 的 `self.onmessage`（只加协议字段）。
   - `test/decoder-analysis-queue.test.ts`。
3. **修改：**
   - **统一结算：** 每个请求有唯一 `requestId` 和 `queued → inflight → settled` 三态，只能经 `settle()` 一处结束。它负责清计时器、一次性通知所有等待者、只把正常结果写缓存、再 `pump()`。
   - **统一退役：** `retireWorker(w)` 解除全部处理器并终止。
   - **统一失败入口：** `error`、`messageerror`、`postMessage` 抛错共用一个入口。先校验事件来自当前 Worker 实例，否则忽略并计数；再退役 Worker、结算在飞行任务。排队任务不失败，留给新 Worker。
   - **熔断：** 连续若干次 Worker 级失败（建议 3 次）后熔断，后续任务快速显式失败，`cancelAll` 后恢复。
   - **缓存：** 缓存键改为 scriptId 加源码字符串全等。崩溃、超时、取消、熔断这类瞬时错误不入缓存；解析失败照旧缓存。
   - **等待者：** `attachToActive` 的 100 ms 轮询改为把等待者挂到同键请求上。删除 :200 那行不可达、且一旦执行会遗弃 Promise 的截断。
   - **队列满：** 不再判终态失败，见决策 D3。
   - **Worker 回显：** 应答增加 `requestId`、`scriptId`、`sourceLength`、`sourceSha256`、`analysisMs`。`result` 对象原样透传。
   - **超时阈值：** 本阶段不定数，等阶段四实测后按预先登记的规则确定（决策 D4）。
4. **影响：** `panel.ts` 调用点（阶段二同步改）。现有“队列上限，36 个失败”一条的预期随 D3 改变，这是语义变更，会在报告里单列。
5. **测试（先红后绿）：**
   - 在飞行时触发 `onerror`，任务立即失败，不推进到超时。
   - 崩溃时已排队的任务在新 Worker 上完成，且不进缓存。
   - 崩溃后新提交的任务立即可执行。
   - 已退役 Worker 迟到的 `error` 和 `message` 对新 Worker 零影响。
   - `messageerror` 同崩溃路径。
   - 熔断与恢复。
   - 瞬时错误不缓存，解析失败仍缓存。
   - 同 scriptId 不同源码不命中缓存。
   - 超时路径与崩溃路径等价。
   - 回显不一致时显式失败。
   - 带种子的随机事件序列下不变量成立：每个 Promise 恰好结算一次；有在飞行任务就一定有当前 Worker；空闲时队列为空。
6. **验收：**
   - 上述全绿且红阶段输出存档。
   - 原有队列测试除 D3 相关一条外不变。
   - `src/**` 无新增类型错误。
   - 真机（阶段六）用删掉 Worker 产物的 TEMP 构建，首个任务 5 秒内显式失败，熔断生效，没有脚本被标为已分析。
7. **依赖：** 阶段三。若最终是 IIFE，Worker 内不能引入带动态 `import` 的 `hash-utils.ts`，改用 WebCrypto；这一点是预期，阶段三的临时构建会给出证据。
8. **回滚：** 还原客户端、Worker、测试三个文件并重建，核对 `dist` 回到阶段三清单。

### 阶段二：手动刷新、页面重置与退休脚本竞态

2. **文件：**

## 六、本方案不覆盖的残余风险

- `background.ts:168` 在插桩暂停期间同步分析脚本，可能长时间占住 Service Worker。

- L1 目标站连接超时的根因仍是 unknown，与本方案无关。
