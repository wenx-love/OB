## 四、执行模型与隔离方案

### 4.1 总原则

**从阶段零到阶段六，原项目目录只被读取，不被写入，也不作为任何工具的工作目录、配置位置或路径参数。** 全部修改、测试、构建和真机运行都在一份隔离的工作副本里进行。原项目只在阶段六通过之后、经用户和 Codex 单独批准的“提升闸门 P”里发生一次变化（见 10.8）。

这样做的理由：

- 原项目里已有的工具行为会自己写文件（2.2、2.3、2.4），在原地运行就无法保证不变。
- 原项目没有版本库，一旦被改，只能靠备份还原。
- 这也让“证明没有变化”对每个阶段都成立，而不只是阶段零。

### 4.2 运行根目录的布局

所有产物放在一个运行根目录下，位置由决策 D14 确定，默认是 `C:\Users\Administrator\TEMP\opencode\p47r\<运行编号>\`（下文写作 `<run>`）。它在原项目之外。

**运行根目录的权限。** 这个 TEMP 目录按当前权限可以被 Codex 沙箱组修改（2.9），新建的子目录会继承这一点。所以推荐在建立 `<run>` 时关闭它的继承：只给我自己的账户和 SYSTEM 完全控制，给 Codex 沙箱组只读。这样审查方能读到全部材料，但改不了。这是对一个新建目录设置权限，不涉及原项目，但仍然是权限改动，需要用户批准（D14）。不批准时，把整个 `<run>` 当作不可信位置对待：每次使用基线和工具之前，先与交付回复里公布过的哈希核对；工作副本本身一直在变，没有固定的哈希可比，它被别人改动只能靠 GU-4（每一处差异都要有出处）事后发现。

```text
<run>\
  baseline\    原项目的基线清单、整树归档（只读保存）、修复前 dist 的固定副本
  controls\    检测工具的自测用假目录树
  tools\       清单、比对、复制、守卫、启动器等工具，以及各自的哈希
  sandbox\     工作副本：全部编辑、测试、构建都在这里
  gitdir\      工作副本的版本库元数据（若 D13 获批），放在 sandbox 之外
  out\         每个阶段的命令日志、标准输出、守卫日志、清单与差异
  evidence\    新产生的真机证据：独占创建、追加式索引
  profiles\    浏览器 profile：一次运行一个，不复用
  tmp\         子进程的 TEMP/TMP，以及 npm 缓存
  review\      交给用户和 Codex 审查的阶段包（位置可由 D14 另行指定）
```

- **路径长度：** 原项目最长相对路径是 120 个字符。运行根目录名保持简短，复制工具会检查每个目标路径并在超过 240 个字符时拒绝。
- **保留策略：** 运行根目录里的任何东西，未经批准不删除；失败的运行记录永不删除。profile 例外：每次真机运行结束后删除，删除前记录文件数和字节数。
- **容量：** 一份归档和一份工作副本各约 100 MB（都含 `node_modules`），每个 profile 约 50 到 200 MB。C 盘可用 81 GB，D 盘可用 386 GB。

### 4.3 六层隔离

没有哪一层单独可靠，所以分层设置，并写明每一层防不住什么。

| 层 | 做法 | 防住什么 | 防不住什么 |
|---|---|---|---|
| L0 位置隔离 | 工作目录、配置文件、工具入口全部位于 `<run>\sandbox`；原项目路径不出现在任何命令行里 | 靠相对路径、`__dirname`、`import.meta.url`、`projectRoot()` 定位的写入（Vitest 缓存、Vite 临时文件、`closeBundle` 复制、`persistRun`） | 源码里写死的绝对路径 |
| L1 路径中和 | 把工作副本里**代码文件**中的原项目根路径和固定 TEMP 路径机械替换成 `<run>` 下的路径，逐文件记录 | 旧脚本被误运行时写原项目、删公用 profile | 运行时拼出来的路径；不在替换范围内的文件 |
| L2 启动器 | 所有命令经一个启动器执行：按阶段的命令白名单、参数与环境检查、完整日志 | 临时起意的命令、带错参数、用 `npx` 触发的额外写入、误跑证据生成脚本和 L1 运行器 | 绕过启动器手工执行的命令 |
| L3 写入守卫 | 给 Node 进程预加载一个文件系统守卫：写入目标不在允许目录内就拒绝并记录 | Node 进程内经 `fs` 的越界写入，包括 Vitest 的工作进程 | 非 Node 进程（Chrome、esbuild 的原生进程、`cmd`、`git`）；不经 `fs` 的写入 |
| L4 输出分离 | 新证据只写 `<run>\evidence`，独占创建；新脚本不带任何默认输出路径 | 新运行覆盖历史证据 | 没有改造的旧脚本（它们被 L2 禁止运行） |
| L5 事后检测 | 每批命令之后对原项目做一次清单比对；阶段首尾做完整比对 | 前面各层的任何漏网 | 它只能发现，不能阻止 |

另有一项不属于技术手段的约定：**静默窗口**（6.6）。原项目和 TEMP 目录上都有其他能写入的主体（2.1、2.9），技术隔离只能管住我自己的进程。

### 4.4 L1 路径中和的细则

- **范围：** `scripts/` 下全部 48 个文件，加项目根目录的 10 个零散代码文件（`.ts`、`.cjs`、`.mjs`、`.js`）。
- **明确不碰：** `docs/`、`test/acceptance/`、`test/fixtures/`、根目录的 3 个日志文件、`test-pages/` 下的 2 个说明文档、`dist/`、`node_modules/`。这些文件里的路径是历史记录，改了就是改证据。
- **映射规则：** 原项目根的正斜杠和反斜杠两种写法都替换为 `<run>/sandbox`；`C:/Users/Administrator/TEMP/opencode/` 前缀替换为 `<run>/profiles/legacy/`。不替换 Chrome 可执行文件的路径（那是只读的公用程序）。
- **记录：** 生成一份中和清单，逐文件写明替换前哈希、替换后哈希、每种映射的替换次数。
- **残留检查：** 替换后在上述范围内搜索原项目根（各种写法）和未替换的 TEMP 字面量，命中数必须为 0。
- **等价性检查：** 中和之前先在原样副本上跑一次 `tsc` 和 Vitest，中和之后再跑一次，两次结果必须逐条相同（见 10.1 的 G0-6）。测试只读取脚本源码做结构断言，不执行脚本，所以这一步能发现中和是否改变了任何断言结果。
- **提升时的还原：** 中和属于工作副本专用的改动，不进入原项目。提升时对每个被中和过的文件做逆映射，并做往返校验：把提升内容再中和一遍，必须与工作副本里的内容逐字节相同。

### 4.5 L2 启动器的细则

- **输入：** 阶段编号加命令编号，不接受自由拼写的命令行。每个阶段的白名单在该阶段开工前随方案一起登记。
- **环境：** 工作目录固定为 `<run>\sandbox`；`TEMP`、`TMP`、`npm_config_cache` 指到 `<run>\tmp`；`NODE_OPTIONS` 由启动器整体设定为“预加载写入守卫”，覆盖外部已有的值并在日志里记下原值。
- **工具入口：** 直接用 `node` 调用工作副本里的入口文件（`node_modules\typescript\bin\tsc`、`node_modules\vitest\vitest.mjs`、`node_modules\vite\bin\vite.js`），不用 `npx`。
- **拒绝条件：**
  - 任一参数或环境变量的值含有原项目根路径（正反斜杠、大小写、`file:///` 形式、`\\?\` 前缀都算）。
  - `--config`、`--root`、`--dir`、`--outDir`、`--outputFile` 解析后不在 `<run>` 之内。
  - `tsc` 不带 `--noEmit`。
  - 目标脚本在“旧脚本禁用清单”“证据生成脚本禁用清单”里，或是 `p47-l1-ob-run.ts`。
  - 系统里存在指向原项目的 `subst` 映射，或 `<run>` 内存在解析到原项目的联接点。
- **日志：** 每次调用记录命令编号、完整参数、工作目录、环境摘要、起止时间、退出码、标准输出与错误输出文件的哈希。
- **限制：** 8.3 短路径名之类的别名靠字符串检查发现不了，由 L3 的真实路径解析和 L5 的事后检测兜底。

### 4.6 L3 写入守卫的细则

- **加载方式：** 一个 CommonJS 预加载模块，包装 `fs` 和 `fs.promises` 的写类函数（写文件、追加、写流、以写方式打开、复制与硬链接的目标、重命名的两端、删除、建目录、截断、改权限、改时间戳、建符号链接），包装后调用 `syncBuiltinESMExports()`，让 ES 模块的具名导入也拿到包装后的函数。
- **判定：** 把目标解析成真实路径（目标不存在时取最近的已存在上级目录的真实路径，再拼回剩余部分）。在允许目录内就放行并记日志；否则抛出明确的错误并记日志。允许目录按命令类别给出，并且永远只在 `<run>` 之内。测试、构建和真机脚本的允许目录是：`<run>\sandbox`、`<run>\out`、`<run>\evidence`、`<run>\profiles`、`<run>\tmp`、`<run>\gitdir`、`<run>\controls`。出审查包的命令另加 `<run>\review`（或 D14 指定的位置）。`<run>\baseline` 写完之后对所有命令只读。
- **对原项目的读取：** 测试、构建和真机脚本读取原项目也会被拒绝并记录。工作副本里的任何东西都不应该需要读原项目；出现读取就说明有硬编码路径漏网。
- **清单与归档工具是例外，因为它们必须读原项目：** 这类工具只有三种（清单、归档、比对），代码量小，随审查包提交；它们只用读权限打开原项目里的文件，先在假目录树上自测，再用于原项目。它们有一部分用 PowerShell 写，不在 Node 守卫的覆盖范围内，所以“它们没有写原项目”靠的是代码审查、自测和首尾清单比对，而不是守卫。
- **自测不碰原项目：** 守卫的“禁止目录”由环境变量传入。自测时把它设成 `<run>\controls` 下的一个假目录，再做三项探针：写禁止目录必须被拒；写允许目录必须成功；读禁止目录必须被拒。这样即使守卫有缺陷，探针也碰不到原项目。
- **确认守卫在 Vitest 的工作进程里生效：** 用一个只存在于工作副本的探针测试读取守卫设置的全局标记。预加载能否被 Vitest 3.2.7 的工作进程继承属于 unverified；如果探针显示没有继承，改用一个只存在于工作副本的包装配置把守卫挂到 `setupFiles` 上，并作为偏差登记。
- **写明的限制：** 守卫只覆盖 Node 进程里经过 `fs` 的调用。Chrome、原生的 esbuild 进程、`cmd`、`git`、PowerShell 不受它约束，这些由 L0、L1、L2、L5 负责。守卫是绊线，不是安全边界。

### 4.7 不采用的做法

- **给原项目加“拒绝写入”的访问控制项，或设只读属性：** 这会改动原项目每个文件的安全描述符或属性，本身就是对原项目的修改，还会影响 Codex 沙箱的访问。如果用户想要这层硬保护，可以自己操作，并在基线清单之前完成。
- **用联接点或虚拟盘符把原路径指到副本：** 需要改动原项目的位置或名字。
- **依赖卷影副本：** 需要管理员权限，本轮会话没有。

## 六、如何证明原项目源码、完整 dist 和历史证据没有变化

### 6.1 比对对象

对原项目整棵树的每个文件和每个目录各记一行，**包含 `node_modules`**（2.3 说明了为什么必须包含）。在每个阶段的入口和出口各做一份完整清单；每批命令之后做一份快速清单。

**关于原生辅助程序：** 读取变更时间和文件 ID 需要调用系统接口。本轮我自己的第一版辅助程序就有结构体对齐错误（第三节第 4 条）。因此规定每个辅助程序必须带自检（结构体大小断言），并把它读到的大小和修改时间与 `Get-Item` 逐项交叉核对，全部一致才允许用于原项目。

### 6.2 判定标准

**硬性条件（任一不满足即判“已变化”）：**

1. 文件集合与目录集合完全相同：没有新增、删除、改名，大小写折叠后也没有冲突。
2. 每个文件的 SHA-256 和大小相同，且两套哈希实现一致。
3. 每一项的修改时间、创建时间、属性相同。
4. 每一项的文件 ID、链接数相同。
5. 每个文件的备用数据流列表相同。

**绊线（出现差异不直接判失败，但必须逐项归因）：**

6. 每一项的 USN 相同。
7. 每一项的变更时间相同。
8. 每一项的安全描述符相同。
9. 变更日志的 ID 相同（ID 变了说明日志被重建，USN 失去可比性）。

**判定结果只有三种：**

- **未变化：** 1 到 9 全部满足。
- **已变化：** 1 到 5 有任一条不满足。立即停止，保留现场，报告差异。不自动还原，因为还原也是对原项目的写入，需要单独批准。
- **不能判定为未变化：** 1 到 5 全部满足，但 6 到 9 有差异。这说明有主体触碰过原项目的元数据，或以相同内容重写过文件。按设计，我方的任何命令都不以原项目为目标，所以这类差异不可能归因到启动器日志里的命令。处理方式是：如实写成“内容未变，但被外部触碰”，列出受影响的条目，由用户裁定是否接受；阶段门槛在裁定前保持未通过。

不允许把第三种结果写成第一种。

**分范围给出结论。** 清单覆盖整棵树，但结论按下表的每一行分别给出，每一行都要单独满足上面的条件。规划时刻各范围的目录摘要如下（算法和完整值见附录 B.1），阶段零的基线必须先与它们对上：

### 6.3 明确排除的字段及原因

**最后访问时间不参与判定。** 做清单需要读取原项目的每个文件，读取可能更新最后访问时间（本机设置是“系统管理，启用更新”）。这是只读核对不可避免的、已知且有界的副作用，在这里事先声明。读取不改内容和修改时间；读取不改变 USN、变更时间和文件 ID，这一点本轮已经在原项目的真实目录树上观测到（2.8）。阶段零仍会在假目录树上再做一次专门的验证，因为本轮的观测只覆盖 D 盘这一个卷和本轮用到的几种读取方式。

### 6.4 检测工具必须先证明自己能发现变化

一个从不报错的检测工具没有证明力。阶段零的第一步是在 `<run>\controls` 的假目录树上植入下列每一类变化，逐类确认工具能发现并归到正确的类别：

- 内容变化（大小不变）、内容变化（大小改变）。
- 新增文件、删除文件、改名、仅大小写改名。
- **相同内容重写**（复制覆盖，保留修改时间）：必须只表现为 USN 变化，这正是 2.2 的情形。
- 只改修改时间；只改属性；只改访问控制列表。
- 删除后以相同内容重建（文件 ID 应当不同）。
- 新增与删除空目录。
- 增加备用数据流、增加硬链接。
- 对照组：只读取、只哈希，必须报告零差异。

阶段零里还有两项发生在工作副本上的对照。按 2.2 的判断，预期结果是：

- 在工作副本里跑 Vitest 之后，工具报告“`dist` 的 6 个静态文件 USN 变了、内容没变”。
- 用不带复制插件的配置再跑一次，工具报告这 6 个文件的 USN 没变。

两项都符合预期，就同时证明了检测工具有效和 2.2 的归因成立。任何一项不符合预期都如实记录：那说明 2.2 的归因有误或检测工具有问题，需要先查清再继续。

### 6.5 独立复核

为了不让结论只依赖我写的清单工具：

- **归档比对：** 阶段零把原项目打成一份 zip 归档，归档里每个条目的哈希与基线清单逐项比对。此后任何时候都可以把原项目与这份归档逐文件比对，不经过清单工具。
- **哈希在生成的当时公布：** 归档和每份基线清单一生成，它们的 SHA-256 就写进当时的回复里。运行根目录所在的位置别人也可能写得到（2.9），所以以回复里的记录为准，不以目录里的文件为准。
- **独立校验脚本：** 提供一个不超过百行的 Node 脚本，只做“遍历、哈希、与清单比对”，供用户或 Codex 自行运行。
- **附录 B 的清单：** 规划时刻的逐文件哈希和目录摘要已在本文给出，目录摘要的算法写明了，可以独立复算。

### 6.6 静默窗口约定

- **开窗前：** 用户确认在窗口期内不让 Codex、编辑器、同步或备份工具、其他会话触碰原项目，并把确认写进阶段记录。
- **两端各记一次：** 进程快照（命令行或工作目录含原项目路径的进程，以及所有 Chrome、Node 进程）；变更日志 ID 与当前位置；项目根的访问控制列表。
- **限制：** 非管理员会话只能看到当前用户可见的进程，看不到其他账户（例如 Codex 沙箱账户）的进程命令行。所以这一条主要靠约定，技术手段只能事后发现。
- **约定同样覆盖运行根目录。** 工作副本、工具和基线被别人改动，后果与原项目被改动一样严重。D14 的权限限制获批时，这一条由权限保证；没有获批时，靠每个阶段首尾与已公布的哈希核对。
- **窗口期内出现无法归因的差异：** 判为 6.2 的第三种结果，保留全部现场，停止，报告。查明原因并重新取基线之后才能重做该阶段。
- **两个阶段之间不在窗口期内。** 这段时间原项目可能被别人读取或触碰，本方案不阻止。每个阶段入口的完整清单要与上一阶段出口的清单比对：有差异就先报告，由用户裁定后才开工。内容层面的差异在查清并处理之前，不进入提升闸门。

### 6.7 可选的增强：一次提权的日志导出（D15）

非管理员只能读到每个文件“最后一条”日志记录的位置，读不到记录内容。如果用户愿意在管理员窗口里执行一次只读的日志导出（从阶段入口记下的位置读到出口），就能得到窗口期内**全部**记录及其原因码，包括“创建后又删除”这种不留文件的操作。把记录里的文件 ID 和上级目录 ID 与清单对照，可以直接证明“窗口期内原项目没有任何日志记录”。没有这一步时，瞬时文件只能靠目录的变更时间和 USN 间接发现。

两点限制：变更日志记录的是哪个文件在什么时候发生了哪一类变化，不记录是哪个账户或进程做的；日志的容量有上限，旧记录会被循环覆盖。11-10 22:48:38 项目那次事件的记录，本轮开始时还在 D 盘日志的有效范围内；TEMP 在 C 盘，那个卷的日志本轮没有查。想用日志确认这两次事件的类型，就要尽早导出。

### 7.3 十项保护措施

1. **原项目里不运行任何东西。** 这一条覆盖上表全部写入者。
2. **工作副本里的证据副本也必须保持逐字节不变。** 每批命令之后核对上表各组的目录摘要和逐文件 USN。
3. **把“证据副本被改写”当作回归信号，而不是可接受的副作用。** 如果在工作副本里跑 Vitest 导致 63 个落盘文件中任何一个被改写，说明流水线输出与归档的证据不一致。处理方式是停止、保留差异、报告，不接受“重新生成后测试通过”。
4. **把 L2/L3 测试的落盘改为默认只校验（D11）。** 默认情况下只比较“将要写入的内容”与“已归档的内容”，不一致就让测试失败并给出差异，不写任何文件。只有显式给出一个位于项目树之外的输出目录时才写，并且拒绝写进项目树。
5. **证据生成脚本列入禁用清单。** 上表里的脚本一律不在任何阶段的启动器白名单里。阶段二会改变面板日志的时序和格式，而这些脚本按旧格式解析日志，重新运行只会产生与历史证据不可比的新文件。
6. **L1 运行器三重拦截。** 启动器按文件名拒绝；路径中和之后，在工作副本里预置一个与它的输出同名的哨兵文件，使它自带的“输出已存在即拒绝”守卫在启动浏览器之前生效；每次阶段出口核对工作副本里的台账副本未变。哨兵文件名要随运行器的输出名同步，由启动器的预检负责。
7. **真机运行的网络隔离。** 所有真机脚本都带 `--host-resolver-rules=MAP * ~NOTFOUND , EXCLUDE 127.0.0.1`，并关闭 Chrome 的后台联网与组件更新。运行期间被动记录所有已附着页面的网络请求，出现任何非本机主机即判该次运行失败。限制：这条规则拦主机名，不拦直接写 IP 的地址；浏览器进程自身的后台流量不在页面级监听范围内。
8. **新证据与历史证据物理分开。** 新证据只写 `<run>\evidence`，文件名带阶段、用途和序号，独占创建，已存在即拒绝。每创建一个文件，就在一份追加式索引里记一行（路径、大小、哈希、创建时间、上一行的哈希），形成可校验的链。
9. **提升时把现有证据排除在外。** 提升清单里不允许出现基线里已有的证据文件和历史报告。需要更正的内容以新文件的形式增加。
10. **不清理。** 运行根目录内的内容未经批准不删除；失败的记录永不删除、不覆盖、不用重跑替代。

### 10.3 阶段一：Worker 崩溃恢复与任务生命周期

1. **问题根因（原方案 P0-1，全部 confirmed）：**

   - `onerror` 不校验事件来自哪个 Worker 实例；`messageerror` 没有处理。
   - 超时、崩溃、取消、销毁四条路径各写各的，没有统一的清理。

| G6-4 | 提升清单草案完整：逐文件的动作、提升前后的哈希、出处阶段；不含任何现有证据文件和旧报告 |
| G6-5 | 原项目自阶段零入口到此刻始终为“未变化”，或每一次例外都有记录和裁定 |

7. **前置依赖：** 阶段一至五全部通过并获批准。
8. **回滚方案：** 工作副本恢复到任一阶段出口。原项目此时仍未改动，无需回滚。

### 10.8 提升闸门 P（不属于七个阶段，需要单独批准）

提升是整个方案里唯一写入原项目的步骤。

- **前提：** 阶段六通过；用户和 Codex 逐项批准提升清单；重新约定静默窗口；原项目当前内容与 M0 相同（不同则先查明原因）。
- **提升的内容：** 改动过的产品源码和配置；新增与修改的测试；登记的新夹具；改造过和新写的脚本；新增的文档；最终构建的 `dist`（整体替换，旧的带哈希文件名的文件按清单删除）。
- **不提升的内容：** 路径中和的结果；工作副本专用文件；`node_modules`；`test/acceptance` 和三个落盘目录里的任何现有文件；旧报告；`registry.json` 和 `budget-ledger.json`。`package.json` 和 `package-lock.json` 在工作副本里本来就不允许变化。
- **新证据是否收进项目：** 可选。收的话放进一个新目录，全部是新文件名，不覆盖任何现有文件。
- **被中和过又被阶段改动过的文件：** 做逆映射后提升，并做往返校验（4.4）。
- **做法：** 先在 `<run>` 下拼出完整的目标树，核对它与“M0 加提升清单”完全相等；然后只用普通的文件复制写入原项目，逐文件核对哈希。**不在原项目里运行任何构建、测试或脚本。** 阶段三的修复只是让 Vitest 不再写 `dist`；在原项目里跑测试仍然会写 `node_modules` 下的缓存，所以提升之后也不在原项目里跑，验证靠“提升后的内容与工作副本逐文件相同”加上工作副本里已经取得的全部证据。用户如果要在原项目里再跑一遍，属于另一项单独的决定。
- **提升后的验证：** 原项目的新清单与 M0 的差异恰好等于提升清单，不多不少；`dist` 的摘要等于工作副本最终构建的摘要；历史证据各组的摘要不变。
- **回滚：** 按步骤日志逆序撤销，或用阶段零的归档还原被改动的文件，然后核对内容与 M0 相同。还原出来的文件内容相同，但 USN、变更时间、可能还有创建时间会不同，这一点事先声明。

## 十一、决策事项 D1—D16

D1—D10 是原方案提出的，这里按五项展开；D11—D16 是本轮因三项新发现和隔离要求新增的。每一项的“是否需要批准”都回答“是”，区别在于为什么需要、不批准时怎么办。

**各项需要在哪个阶段之前有结论：** 阶段零之前是 D12、D14、D15；阶段三之前是 D1、D2、D11、D13、D16；阶段一之前是 D3 和 D4 的规则；阶段二之前是 D5、D6、D7、D10；阶段四之前是 D8、D9。

### D1：Worker 输出格式

- **原始问题：** `vite.config.ts` 把 Worker 配置写在 `build.worker` 下，Vite 6.4.5 不读这个位置，实际输出是默认的 IIFE；源码里的构造参数却是 `{ type: 'module' }`。目前能运行，属于碰巧兼容。
- **推荐方案：** 候选 A 是顶层 `worker.format: 'es'` 配 module 构造；候选 B 是 `format: 'iife'` 配 classic 构造。两者各在工作副本里构建到独立目录并真机加载，按证据定案。默认选 A；A 有任一验收项不过就用 B。
- **理由：** A 让配置、源码声明和产物三者一致，同一批 Babel 依赖在主构建里已经以 ES 模块运行。B 是唯一已经被真机证明能加载的形态，适合作退路。
- **风险：** A 可能把 Worker 拆成多个文件，需要确认扩展环境下模块 Worker 能加载这些文件（unverified）。B 需要改一行产品源码的构造参数；IIFE 输出遇到依赖图里的动态 `import` 时的行为没有验证过。无论选哪个，`dist` 的文件名和哈希都会变。
- **是否需要批准：** 是。改构建配置和一行产品源码。需要批准的是“默认 A、不过则 B”这条规则，以及最终定案。

### D2：构建戳的位置

- **原始问题：** 没有任何机制能证明 `dist` 是由当前源码构建的。上一轮的全部“修复后”真机证据都跑在一份早于最终源码的构建上，事后才发现。
- **推荐方案：** 在 `dist` 里写一个构建戳文件，随扩展包走。内容是输入文件的哈希清单、产物文件的哈希清单、Vite 与 Rollup 版本、Worker 产物名与格式，不含时间戳。真机脚本启动前读取并比对，不符就拒绝运行。备选是把戳放在项目根目录、不进扩展包。
- **理由：** 放在 `dist` 里，戳和产物不会分离，装载的那份扩展自己就能说明来历。不含时间戳才能保证两次构建逐字节相同。
- **风险：** 扩展包里多一个文件。戳只能证明构建时刻的对应关系，构建之后手工改 `dist` 要靠产物哈希清单和校验脚本发现。
- **是否需要批准：** 是。它改变发布包的内容。不批准放进 `dist` 时用备选位置。

### D3：队列满的处理

- **原始问题：** 客户端队列上限 64，超出的任务被判为终态失败并写入缓存，不强制刷新就不会再分析。上一轮 run2 里面板的脚本总数第一次变化就是 65，最后是 477，这与“前 64 个被接受、其余 413 个因队列满被拒绝”相符。这是从计数推出来的（suspected），当时没有逐个读取脚本的状态。
- **推荐方案：** 队列满时客户端返回明确的“未受理”，不算失败、不进缓存。协调器把脚本标为“延后”，队列腾出位置时按发现顺序自动补投，界面上显示延后数量。备选是取消上限。
- **理由：** 脚本源码本来就全部留在面板内存里，延后不增加内存占用；保留一个有界的队列更容易推理和测试。
- **风险：** 页面持续产生新脚本时，延后列表会一直增长，需要显示数量并在超过阈值时提示。按发现顺序先到先服务，目标脚本可能排在大量小脚本后面，等待时间由阶段四实测。现有“队列上限，36 个失败”的用例预期要改，这是语义变更。
- **是否需要批准：** 是。改产品行为和一条既有测试的预期。

### D4：超时规则

- **原始问题：** 10 分钟的超时依据的是主线程的 145 秒。Worker 里先后分析 hpailist-2 和 512 KB 脚本，页面内计时合计 439 秒（两个脚本各自的耗时当时没有分开记录）。正常的长分析有可能被当成挂死而终止。
- **推荐方案：** 测量之前先登记规则：超时取“30 分钟”与“参考输入上实测的最大单脚本 Worker 耗时的 6 倍”两者中较大的一个。阶段一写入 30 分钟作为暂定值，阶段四实测后在该阶段出口定终值。
- **理由：** 超时的用途是发现挂死，不是限制性能。规则先于测量登记，数值就不能照着结果凑。
- **风险：** 真正挂死时至少 30 分钟才被发现；并发度为 1，这段时间里后面的脚本全部等待，所以必须同时有“分析中”和已用时间的显示（D5）。倍数和下限是经验取值；参考机器不等于用户的机器。
- **是否需要批准：** 是。需要批准的是规则本身。

### D5：面板进度显示与日志格式

- **原始问题：** 修复后有源码的脚本在发现时不再刷新计数，队列忙的时候数字停住；没有“分析中”和“失败”的计数；完成和失败的日志行不带脚本标识。上一轮承诺的“能显示分析进度和失败原因”没有做到，这也是性能判据误判的直接条件。
- **推荐方案：** 面板新增“分析中”“失败”两个计数（D3 获批时再加“延后”）；发现脚本时立即刷新计数；完成和失败的日志行在**末尾**追加脚本标识，原有前缀保持不变。
- **理由：** 这是让进度和失败可见的最小改动。保留前缀是为了不破坏按前缀解析日志的旧测试和脚本。
- **风险：** 要改 `panel.html`；读面板 DOM 的布局检查脚本需要复核；依赖“发现”和“完成”两行相邻配对的旧脚本在异步之后会配对错位，与是否追加标识无关，这些脚本已列入禁用清单。
- **是否需要批准：** 是。这是可见的界面改动。

### D6：后台对已清空脚本的守卫

- **原始问题：** `background.ts:228-239` 在异步取到源码之后才发 `script-discovered`，不检查该脚本是否仍属于当前文档；面板收到后会取消这个 scriptId 的退休标记（`panel.ts:1205`）。状态是 suspected，没有复现过。
- **推荐方案：** 先写一个能复现的测试。复现成立，才在后台加一行守卫：收集器里已经没有这个脚本对象时不外发。复现不成立，就不改 `background.ts`，这一项维持 suspected。
- **理由：** `background.ts` 紧邻捕获流水线，不应该凭猜测改它。
- **风险：** 面板一侧无法区分“迟到的旧脚本”和“新脚本”，所以阶段二的提交校验挡不住这种情况；如果不加守卫又确实存在这个问题，旧文档的脚本会被当作当前脚本分析并显示。守卫如果写错，会丢掉合法脚本。
- **是否需要批准：** 是。涉及 `background.ts`；复现结果出来后再请用户裁定。

### D7：捕获目标的筛选与提示

- **原始问题：** `startRuntimeCapture` 遍历全部候选时不看脚本是否已退休，页面重置后旧文档的候选可能被当成断点目标发给引擎（引擎拿到失效 scriptId 的后果 unverified）。这个问题在 Worker 改动之前就有。另外，分析改成异步之后，用户可能在目标脚本还没分析完时就点开始捕获，得到一次不完整的捕获而没有任何提示。
- **推荐方案：** 构造目标时跳过退休脚本的候选，并在“未纳入捕获”的提示里列出；还有脚本在分析或延后时，在提示里写明数量。不阻止开始捕获。
- **理由：** 验证路径和手动模式已经按“退休脚本不参与”处理，这里只是对齐。它只减少已失效文档的目标，不改引擎、不改捕获时机。
- **风险：** 必须用测试证明“没有退休脚本时目标清单逐字节不变”。只提示不阻止，用户仍可能得到不完整的捕获；改成阻止会改变捕获时机，超出本轮范围。
- **是否需要批准：** 是。它改变发给捕获引擎的目标集合。

### D8：主线程长任务阈值

- **原始问题：** 上一轮没有事先登记的验收线，拿 300 秒窗口和 10 秒窗口的数字做了对比。
- **推荐方案：** 从导航到目标脚本提交并渲染完成的整个窗口内，面板主线程的单个长任务低于 500 ms；所有 50 ms 以上的长任务逐条列出。测量前登记，测量后不改。
- **理由：** 修复前是 150 000 到 210 000 ms 的单次阻塞；上一轮修复后的构建在导航后头 10 秒里记录到的最长任务是 250 ms。500 ms 留有余量，又足以说明阻塞已消除。
- **风险：** 结果落地阶段（约 2.4 MB 的结果反序列化、983 个候选、约 1000 张卡片渲染）从未被测量过，有可能超过 500 ms。超过就按登记的标准判失败；是否另做渲染优化是单独的一项，需要另行批准。后台或被遮挡窗口的计时器节流会干扰长任务观测。
- **是否需要批准：** 是。阈值由用户定。

### D9：L1 运行器的完成闸门

- **原始问题：** `scripts/p47-l1-ob-run.ts:504-522` 的 `analysisSettle` 用的是同一种“计数稳定”判据。在 Worker 构建下，它可能在目标脚本还在分析时就放行，随后在断点覆盖闸门被拦下，而那时一次页面加载的预算已经花掉。
- **推荐方案：** 把这个闸门改成按目标脚本判定（经 D10 的钩子），等待上限按阶段四的实测重新设定，同步更新结构测试。不运行 L1。
- **理由：** 它与性能脚本的判据同源，现在一起改，可以避免下一次 L1 白白消耗预算。
- **风险：** 不运行 L1 就无法端到端验证这次改动，证据只有结构测试和本机页面上的演练。它把 D10 的钩子带进了 L1 路径。运行器写入 L1 证据目录的方式不在这次改动范围内。
- **是否需要批准：** 是。不批准时，把它记为“下一次 L1 之前必须完成的前置条件”。

### D10：面板只读测试钩子

- **原始问题：** 面板的分析状态是模块私有的，DOM 只有全局计数，从外部无法知道某个脚本的结果是否已经提交。性能判据的缺陷根源在这里。
- **推荐方案：** 在面板页上挂一个只读对象，提供页面纪元、逐脚本的状态快照、客户端队列统计、按 scriptId 取已提交结果。全部返回副本，没有任何写操作。先例是后台已有的 `__obRecoverTest`。
- **理由：** 没有它，只能回到依赖 DOM 计数和日志的间接判据，而那正是上一轮出错的地方。
- **风险：** 发布包里多一个调试入口（只能从扩展页上下文访问）；测试有可能因此依赖内部结构。
- **是否需要批准：** 是。属于产品代码改动。不批准时，G4-1 无法按现在的定义满足，完成判据需要重新设计。

### D11（新增）：L2/L3 落盘默认只校验

- **原始问题：** 一次普通的 `vitest run` 可以静默覆盖 47 个历史验收文件，而测试回读的是刚写进去的内容，所以自己还会通过（2.4、8.2）。
- **推荐方案：** 默认只比较“将要写入的内容”与“已归档的内容”，不一致或文件缺失就让测试失败并给出差异，不写任何文件。只有通过环境变量显式给出一个位于项目树之外的输出目录时才写；给的目录在项目树内就拒绝。辅助函数返回实际使用的目录，测试的回读跟着走。
- **理由：** 这样历史证据就成了回归基准，流水线输出一旦变化，测试会失败而不是悄悄改掉证据。
- **风险：** 改的是产生证据的测试辅助代码，最容易在不经意间削弱断言，所以配了断言保持检查。以后流水线输出需要有意变更时，必须走一次显式的、经批准的重新生成。全新检出、缺少归档文件时测试会失败，这是预期行为。
- **是否需要批准：** 是。不批准时退回“只检测”：每次 Vitest 之后核对 63 个文件，有变化即停止。

### D12（新增）：工作副本模式与一次性提升

- **原始问题：** 原项目没有版本库；工具在原地运行会自己写文件；还有另一个主体对它有写权限。
- **推荐方案：** 阶段零到阶段六全部在工作副本里进行，原项目只在阶段六之后的提升闸门里变化一次。备选是每个阶段批准后各提升一次。
- **理由：** 一次性提升让“原项目未变化”对每个阶段都可证明，审查的是一份完整的变更集，中途任何阶段失败都不留痕迹。
- **风险：** 原项目会在更长时间里保持现在这个已知有缺陷的状态。提升是一次较大的写入，而且按设计不在原项目里重跑测试。提升之前 Codex 在原项目里看不到改动，审查依赖审查包（D14）。
- **是否需要批准：** 是。它决定了所有阶段的执行方式。

### D13（新增）：工作副本使用版本库

- **原始问题：** 没有版本控制时，阶段之间的差异和回滚只能靠清单和整树归档，可行但笨重。此前有一轮明确禁止创建 Git 提交。
- **推荐方案：** 只在工作副本上使用 Git，元数据目录放在工作副本之外，跟踪源码、测试、脚本、文档和配置，不跟踪 `node_modules`、`dist` 和证据目录。标签依次是原样副本、路径中和之后、每个阶段的出口。原项目永远不初始化为版本库。本机已有 Git 2.55。备选是每个阶段出口存一份整树归档加清单。
- **理由：** 标签能给出精确的差异和可核对的回滚点。
- **风险：** Git 的换行转换之类的行为可能改动工作副本里的字节，所以必须关闭自动换行转换，并在每次检出后用清单核对。清单仍是判定依据，Git 只是便利工具。
- **是否需要批准：** 是。它重新界定了此前“不创建 Git 提交”那条禁令的适用范围，需要用户明确同意；不同意就用备选。

### D14（新增）：运行根目录的位置与权限、归档副本、审查包的位置

- **原始问题：** 原方案把各阶段的备份放在 `C:\Users\Administrator\TEMP\opencode` 下，本文新设的运行根目录默认也在这里。本轮查明这个目录上有给 Codex 沙箱组的显式“修改”权限，并继承到所有子项（2.9）。照原样做，工作副本、基线清单、整树归档和检测工具都可以被别人改动。另外，TEMP 可能被清理，只有一份归档就是单点。
- **推荐方案：**
  - 运行根目录仍用 `C:\Users\Administrator\TEMP\opencode\p47r\<运行编号>`，但建立时关闭它的继承：我自己的账户和 SYSTEM 完全控制，Codex 沙箱组只读，不给其他账户权限。设置前后各读一次访问控制列表并记入阶段记录。
  - 归档和每份基线清单的 SHA-256 在生成的当时写进回复，以回复为准。

  - 初次分析未完成时刷新，两个请求各自通过身份检查、各追加一次。
  - 连点两次刷新，两个循环交错。
  - 刷新循环迭代的是活的 Map，会把刷新期间新发现的脚本再强制分析一遍。
- **新旧请求如何区分：** 无法区分。客户端缓存只按 scriptId，面板的续延不带请求标识。
- **是否需要代次：** 需要两级：页面纪元，和每个脚本的请求序号（只有最新请求可以提交）。
- **是否必须校验 scriptHash：** 面板内用源码字符串全等更强也更便宜。SHA-256 用来核对 Worker 回显和留证。`DiscoveredScript.hash` 只取前 1000 字符加长度（`script-collector.ts:126-134`），不能当身份用。
- **旧结果覆盖新结果：** 同一脚本对象的源码不变，两次结果内容相同，实际危害是重复和状态错乱。旧请求的瞬时错误晚到时会给已成功的脚本写上 `analysisError`（:1241），成功提交也不清旧错误。

### P0-3 的各问

- **重置时刷新循环：** 不会停。取消后循环继续，并在新 Worker 上发起新的强制分析。
- **旧脚本集合是否仍会提交：** 捕获激活时 Map 不清空，旧脚本对象仍通过身份检查，会被重新分析并提交。捕获未激活时 Map 被清空，但挂起的迭代器会继续遍历之后插入的新页脚本，造成新页候选重复。
- **退休脚本是否重新入队：** 会，经由刷新循环。
- **捕获是否使用旧页脚本：** `startRuntimeCapture` 遍历 `allCandidates` 时不查退休状态。引擎拿到旧 scriptId 后的实际后果属于 unverified。
- **页面身份检查：** 目前只有对象身份一项，没有纪元，也没有退休检查。
