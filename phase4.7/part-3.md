
## 九、阶段依赖、执行顺序与阶段门槛

### 9.1 执行顺序

```text
阶段零 → 阶段三 → 阶段一 → 阶段二 → 阶段四 → 阶段五 → 阶段六 → 提升闸门 P（另行批准）
```

阶段编号沿用原方案的名称，执行顺序不按编号。阶段三提前的三个理由不变：`dist` 已经过期，不先修构建，后面的真机验证都跑在来历不明的产物上；Vitest 目前会写 `dist`；Worker 的输出格式决定阶段一协议里哈希的实现方式。

每个阶段结束后停下，等用户和 Codex 审查该阶段的审查包，批准后才开始下一阶段。

## 十、阶段计划

各阶段的“涉及文件”都指工作副本 `<run>\sandbox` 里的对应文件；原项目不动。“回滚”都指把工作副本恢复到上一阶段出口的快照（D13 获批时用工作副本版本库的阶段标签，否则用该阶段出口的整树归档），重建，并核对与上一阶段出口清单逐项一致。回滚不删除任何证据和失败记录。

### 10.1 阶段零：基线冻结与隔离验证

1. **问题根因：** 目前没有一份与最终代码树对应的基线（上一轮的 `tsc` 结果和 `dist` 都早于最终源码）。原方案的阶段零打算在原项目里直接跑 `tsc` 和 Vitest，这会写原项目（2.2—2.4）。
2. **涉及文件：** 原项目零改动。新建的只有 `<run>\tools` 下的工具，以及工作副本里的三类专用文件：路径中和的结果、不带插件的对照配置、L1 运行器的哨兵文件。三类都登记在“工作副本专用文件清单”里，永不提升。
3. **工作内容（按顺序）：**

   2. 在 `<run>\controls` 的假目录树上自测全部工具（6.4 的每一类变化、守卫的三项探针、辅助程序自检）。此时不接触原项目。
   3. 开启静默窗口，记录两端信息的第一份。
   4. 对原项目做第一份完整清单 M0（两套哈希实现）。
   5. 把 M0 与附录 B 逐项比对。规划时刻之后的任何差异先解释，再继续。
   6. 把原项目打成 zip 归档，逐条目与 M0 核对；按 D14 存第二份。

   9. 从归档（不是从原项目）展开出工作副本，逐文件与 M0 核对。
   10. 在**原样**的工作副本上运行：`tsc --noEmit`；Vitest（原配置）；Vitest（不带复制插件的对照配置）。从第 9 步到第 11 步之间，工作副本里的旧脚本还保留着指向原项目的路径，这段时间只执行这三条命令，不做任何别的事。

   12. 在**中和后**的工作副本上重跑 `tsc --noEmit` 和 Vitest，与第 10 步逐条比对。
   13. 核对工作副本里的证据副本（7.3 第 2、3 条）。
   14. 对原项目做最后一份完整清单 M1，与 M0 按 6.2 分层比对；记录静默窗口两端信息的第二份。

### 10.3 阶段一：Worker 崩溃恢复与任务生命周期

### 10.6 阶段五：主线程与 Worker 完整结果一致性

1. **问题根因（原方案 P1-3，confirmed）：**
   - `scripts/p47-worker-exec-verify.ts` 只回传数量、JSON 长度、前五个名字和一个 32 位滚动哈希，且没有经过 `DecoderAnalysisClient`。
   - `test/decoder-analysis-consistency.test.ts` 用同线程的 `structuredClone` 加 `JSON.stringify`，后者会丢信息。
   - `discoverDecoders` 确实会产生 JSON 丢失的值：不传 scriptId 时键存在且值为 `undefined`（`decoder-discovery.ts:146`、`442-444`）；负数字面量取负会得到 `-0`（`:433`）。
   - 主线程一侧此前是 Node 临时脚本，输出未入档；512 KB 输入没有主线程对照。主线程与 Worker 的栈深度和内存上限不同（A6，unverified）。
2. **涉及文件：** 重写 `test/decoder-analysis-consistency.test.ts`；新增 `scripts/p47-consistency-verify.ts` 及其专用的测试页构建配置（输出到 `<run>\out`，不进 `dist`）；`scripts/p47-worker-exec-verify.ts` 保留，更正它“足以判定一致性”的注释。
3. **预期修改内容：**
   - **双哈希：** 每份输出算两个 SHA-256，一个保留键顺序，一个键排序，两者都必须相等；只有保序版不等时单独报告为字段顺序不同。
   - **键白名单：** 按接口定义校验，出现未声明的字段即失败。
   - **四方对照（同一源码、同一参数）：** Node 主线程调原始函数；Node 线程里加载真实的 Worker 入口，跨真实的结构化克隆边界；Chrome 主线程调原始函数；Chrome 里由产品客户端驱动 `dist` 里的那个 Worker 产物（记录其哈希）。
   - **传输：** 每一方在自己的环境里规范化并算哈希。浏览器两方把全文发到本机服务落盘，Node 再独立算一次，两次必须一致。结果不经 CDP 按值返回。
   - **输入矩阵：** 参数（scriptId 和 URL 传与不传的各种组合）；Unicode（中文、emoji、非 ASCII 标识符、孤立代理项、U+2028、NUL、BOM、CRLF）；数值（`-0`、溢出为无穷的字面量、超出安全整数的数、BigInt）；可选字段（有无候选、匿名函数、非字面量实参）；解析失败（至少四类语法错误，加空源码）；大输入（hpailist-2、512 KB 合成脚本、`real-samples` 里三份 27 万到 66 万字节的样本，只作输入，不用其 `expected.js`，不计为真实站点证据）；嵌套深度（逐步加深，并列报告四方各自开始失败的深度）。
4. **可能影响的其他模块：** 只涉及测试和脚本。新增的输入夹具放在一个新的专用目录里，不放进任何证据目录。发现真实差异时不在测试里放宽，按缺陷上报。

### 10.8 提升闸门 P（不属于七个阶段，需要单独批准）

提升是整个方案里唯一写入原项目的步骤。

- **前提：** 阶段六通过；用户和 Codex 逐项批准提升清单；重新约定静默窗口；原项目当前内容与 M0 相同（不同则先查明原因）。
- **提升的内容：** 改动过的产品源码和配置；新增与修改的测试；登记的新夹具；改造过和新写的脚本；新增的文档；最终构建的 `dist`（整体替换，旧的带哈希文件名的文件按清单删除）。
- **不提升的内容：** 路径中和的结果；工作副本专用文件；`node_modules`；`test/acceptance` 和三个落盘目录里的任何现有文件；旧报告；`registry.json` 和 `budget-ledger.json`。`package.json` 和 `package-lock.json` 在工作副本里本来就不允许变化。
- **新证据是否收进项目：** 可选。收的话放进一个新目录，全部是新文件名，不覆盖任何现有文件。
- **被中和过又被阶段改动过的文件：** 做逆映射后提升，并做往返校验（4.4）。
- **做法：** 先在 `<run>` 下拼出完整的目标树，核对它与“M0 加提升清单”完全相等；然后只用普通的文件复制写入原项目，逐文件核对哈希。**不在原项目里运行任何构建、测试或脚本。** 阶段三的修复只是让 Vitest 不再写 `dist`；在原项目里跑测试仍然会写 `node_modules` 下的缓存，所以提升之后也不在原项目里跑，验证靠“提升后的内容与工作副本逐文件相同”加上工作副本里已经取得的全部证据。用户如果要在原项目里再跑一遍，属于另一项单独的决定。
- **提升后的验证：** 原项目的新清单与 M0 的差异恰好等于提升清单，不多不少；`dist` 的摘要等于工作副本最终构建的摘要；历史证据各组的摘要不变。
- **回滚：** 按步骤日志逆序撤销，或用阶段零的归档还原被改动的文件，然后核对内容与 M0 相同。还原出来的文件内容相同，但 USN、变更时间、可能还有创建时间会不同，这一点事先声明。
