## 十、构建、`dist` 与构建戳（R14、R15）

### 10.1 Worker 配置与格式一致性

- `worker` 必须位于 Vite 配置的**顶层**，不能在 `build` 下。
- 产物格式必须与构造参数一致：
  - 候选 A：`worker.format: 'es'` + `new Worker(..., { type: 'module' })`。
  - 候选 B：`worker.format: 'iife'` + classic 构造。
- **历史文义更正：** 旧真机证据是“IIFE 产物 + module 构造”，不是候选 B；候选 B 未被验证。旧 V0 的两次原样构建也不能替代 A/B 各自的加载验证。
- D1 仍未批准；V2 不选定 A 或 B。阶段三必须对 A、B 各自构建到独立目录、各自真机加载、各自记录产物清单；定案由用户在阶段三出口批准。

### 10.2 构建输入闭包

构建戳的输入清单必须覆盖：

| 类别 | 内容 |
|---|---|
| 源码 | `src/**/*.ts`（含 worker 入口、panel、background、sandbox、core） |
| 静态资源 | `src/extension/**/*.html`、`*.css`、`manifest.json`、图标 |
| 配置 | `vite.config.ts`、`tsconfig.json`、`package.json`、`package-lock.json` |
| 环境 | Node、Vite、Rollup、TypeScript 版本；影响产物的环境变量 |
| 排除 | `dist/**`、`node_modules/**`（版本由 lockfile 固定）；构建戳自身 |

- 所有路径使用**根相对路径**，不使用绝对路径。
- 构建戳只记录**输入哈希 + Vite 版本**（D12）；不含时间戳、不含自身哈希、不含产物哈希。
- 产物哈希、Rollup/Node/TS 版本、完整文件清单放在 `dist` 外的旁文件：`<run>\out\build\<id>\artifacts.json`。
- D2（构建戳位置）仍未批准；阶段三进入前必须由用户决定。候选位置：`dist/build-stamp.json` 或项目根 `build-stamp.json`；V2 不选。

### 10.3 可复现构建

1. 在 `<run>\out\build\a` 与 `<run>\out\build\b` 两个独立目录各构建一次，输入相同。
2. 两次产物的逐文件 SHA-256 必须相同；文件清单必须相同；构建戳必须相同。
3. 在两个不同的绝对路径下各构建一次，产物必须相同；任何差异都说明绝对路径进入了产物。
4. 扫描 `dist/**`：不得出现工作副本绝对路径、盘符路径、`file://` 形式、用户名路径。
5. 任一失败：阶段三不通过；不得用“只差一点”放行。

### 10.4 `dist` 校验脚本

只读校验五项：

1. 构建戳的输入清单与当前源码逐文件一致。
2. `panel.js` 引用的 Worker 产物存在，文件名与构建戳一致。
3. Worker 产物的格式特征与构造参数匹配。
4. `panel.js` 不含主线程的 `discoverDecoders(` 调用。
5. 四个入口文件齐全（background、devtools、panel、sandbox）。

负例：缺 Worker 文件、改动一个输入文件、把 Worker 产物替换成 IIFE 而构造仍是 module——三种都必须报错。

### 10.5 测试与构建的写入卫生

- Vitest 在原配置下不得写 `dist`：修复后运行一次，守卫日志对 `dist` 的写入为 0，6 个静态文件 USN 不变。
- 对照实验：独立牺牲副本上“原插件 / 无插件”各跑一次，记录实际写入；原项目永不运行。
- 不得把“每次触发两次”预设为通过条件；频次是 `UNVERIFIED`。
- `tsc` 一律 `--noEmit`；阶段零与阶段六都必须在阶段记录里写明。

### 10.6 旧构建证据

- 旧 `dist`（`panel.js` 为 `accfac09…`）不得用于新源码的任何验收。
- 修复前基线使用阶段零固定的 `dist-before` 副本；其可信性限制（TEMP 可写、只有两个文件有独立旁证）必须随证据一起记录。
- 任何“修复后”结论必须写明所加载 `dist` 的摘要与构建戳；不符即拒绝运行。

## 十一、只读钩子、独立取证与完整一致性（R17、R19）

### 11.1 生产钩子的边界

- 严格按 §3.3：只有 `?obTest=1` 挂载；字段白名单；不返回源码、候选内容、调用位置。
- 不得为完整结果比较而在生产钩子上新增“取已提交结果”“取源码”“取候选”方法。
- 键集合白名单测试必须覆盖：缺字段、多字段、字段类型、冻结、门控。

### 11.2 面板提交的验证

面板提交通过钩子验证：

- 目标脚本的 `state === 'committed'`。
- `committedCandidates` 等于参考值（例如 983）。
- `requestSeq` 与目标请求一致。
- `enqueuedAt ≤ startedAt ≤ settledAt`。
- 脚本记录对应的页面由运行装置记录；钩子本身不返回 `epoch`。
- 两个间隔 2 秒的钩子快照里，同一脚本的 `requestSeq` 与 `committedCandidates` 相同。

这只能证明“面板提交了多少”，不能证明“结果内容与 Node 完全一致”。内容一致性由 §11.3 的独立取证和 §11.4 的四方比较完成。

### 11.3 独立测试取证（不扩大生产钩子）

在隔离的测试环境中：

1. 一个**测试专用页面**（构建到 `<run>\out\harness`，不进入产品 `dist`）加载产品 `decoder-analysis-client` 与产品 Worker 产物；记录 Worker 产物哈希。
2. 用同一份夹具源码、同一 `scriptId`、同一 URL 发起分析。
3. 用类型保真编码器（见 §11.4）序列化**完整结果**。
4. 通过本机回环 POST 到测试服务，落盘到 `<run>\evidence`，独占创建。
5. Node 读取落盘全文，独立计算哈希；浏览器内哈希与 Node 哈希必须相等。
6. 该取证不使用面板 DOM，不使用生产钩子；它不是产品出口。
7. 阶段五的 Chrome 侧必须使用**产品 Worker 产物**，不是复制品；记录产物哈希。

### 11.4 完整一致性（R19）

- **类型保真编码：** 区分 `undefined` 与缺失、`-0`、`NaN`、`±Infinity`、孤立代理项；遇到函数、Map、类实例等不可序列化值时显式报错，不得静默丢弃。
- **两个哈希：** 每份输出计算
  - `hashOrdered`：保留键顺序；
  - `hashSorted`：键排序后计算。
- **比较规则：**
  - 四方（Node 主线程、Node 线程加载真实 Worker 入口、Chrome 主线程、Chrome 产品客户端驱动 `dist` Worker）各自的 `hashOrdered` 必须四方相等。
  - 各自的 `hashSorted` 必须四方相等。
  - **不要求** `hashOrdered` 等于 `hashSorted`；若不等，单独报告“字段顺序不同”，不作为失败。
- **完整深比较：** 若哈希不等，逐字段深比较并定位首个差异；不得只比较数量、长度、前几个名字或滚动哈希。
- **子进程替代：** 若无法直接在 Node 线程加载 TypeScript Worker 入口，改用子进程/独立进程时必须明确标注为降级覆盖，不能仍称“四方原定义通过”。
- **失败不掩盖：** 不允许用投影、删字段、只比子集的方式让比较通过。

### 11.5 性能测量

- 窗口期内不对被检页做 `Runtime.evaluate`；活性用心跳脚本。
- 目标识别用钩子（scriptId、URL 哈希前缀、提交计数、时间戳）。
- 长任务以面板内 `longtask` 为主，CDP 往返只作旁证。
- 测量前登记 D8 阈值；D8 未批准则阶段四不能关闭性能验收（可做技术测量，但不得记为通过）。
- 修复前后使用相同启动参数、相同窗口规则；不同口径的数字不得相除，改善倍率记 `n/a`。
- 结果导出在窗口结束后进行；导出不是窗口的一部分。

## 十二、历史证据保护（R20、R21、R22）

### 12.1 三条写入边界

| 对象 | 规则 |
|---|---|
| 原项目 | 阶段零至六只读；不改源码、配置、测试、`dist`、证据、ACL、属性 |

| 新证据 | 只写 `<run>\evidence`；独占创建；文件名带阶段与序号；哈希链索引 |

**参考样本与观测样本物理隔离：** `reference/` 只能由独立来源写入，`observed/` 只能由 OB-Recover 运行写入；两者不得合并、不得互相覆盖、不得由捕获/验证/替换输出写回 `reference/`。这一条沿用 `registry.json` 的硬规则。

### 12.2 三个实验必须隔离

| 实验 | 位置 | 用途 | 禁止 |
|---|---|---|---|
| 原样副本 | `<run>\out\exp\pristine-<id>` | 原配置跑 `tsc`/Vitest，取基线 | 不得与中和副本混用 |
| 无插件对照 | `<run>\out\exp\no-plugin-<id>` | 去掉复制插件，验证 `dist` 是否仍被写 | 不得复用原样副本 |
| 中和副本 | `<run>\sandbox` | 路径中和后的工作副本 | 不得把中和结果带回原样副本 |

每个实验有独立的整树清单；实验之间不共享可写目录。原项目永不参与实验。

### 12.3 `persistRun` 与 D11（待批准）

D11 仍未批准。V2 给出两种执行方式：

**D11 获批：**

## 十三、“未变化”的证明（R24）

### 13.1 字段

| 字段 | 说明 |
|---|---|
| 路径集合 | 文件与目录；大小写折叠键；无新增/删除/改名 |
| 大小 | 字节数 |
| 内容哈希 | 两套独立实现（PowerShell / Node）；逐文件一致 |
| 修改时间、创建时间 | 100 纳秒原值 |
| 属性 | 原始位值 |
| 文件 ID、链接数 | 句柄查询 |
| 变更时间 | 句柄查询 |
| USN | 只读查询 |
| 安全描述符 | 属主/属组/DACL 的 SDDL 哈希 |
| 备用数据流（ADS） | 每个流的名称 + **内容哈希**；见 13.2 |
| 最后访问时间 | 记录但不参与判定 |

### 13.2 ADS 的强/弱声明

- 只有对每个 ADS 的**内容**计算哈希，才能声明“ADS 未变”。
- 只比较名称和大小不构成内容证明。
- 若某些流无法读取：标记 `ADS-UNVERIFIED`，并缩小声明范围为“主数据流与可读流未变”，不得写“绝对未修改”。

### 13.3 判定

| 结果 | 条件 |
|---|---|
| `unchanged` | 路径、内容、元数据、ADS（或已缩小声明）、USN、变更时间、SDDL 全部满足 |
| `changed` | 路径/内容/元数据任一不满足；停止并报告 |
| `cannot-determine` | 仅绊线差异，且无法归因；记录 `source-unknown`，不判为未变化 |

### 13.4 不归因原则

- 不得从“设计上不访问”推断“变化必由外部主体造成”。
- 出现无法解释的变化：记录 `source-unknown`，停止，保留证据；不写“Codex 改的”“用户改的”或任何具体主体。
- 归因只能来自启动器日志、命令记录或用户书面确认。

### 13.5 阳性对照

检测工具必须先在假目录树上证明能发现：

- 内容变化（大小不变/改变）、新增、删除、改名、仅大小写改名。
- 相同内容重写（只 USN 变化）。
- 只改时间/属性/ACL。
- 删除后重建（文件 ID 变化）。
- 空目录增删。
- ADS 增加、硬链接增加。
- 只读对照组：零差异。

检测工具未通过阳性对照，不得用于原项目。

### 13.6 分范围结论

源（`src`/`scripts`/测试代码/配置）、完整 `dist`、历史证据三组分别给结论；每组有自己的摘要与逐文件清单。不能用一个总哈希代替分范围结论。

## 十四、安全指标（不得降低）

| 指标 | 定义 | 判定 |
|---|---|---|
| False Replacement | 不应替换却被替换的调用点数 | 必须 = 0 |
| Source Integrity | 原始脚本 SHA-256 三处一致（reference/observed/捕获读取） | 必须 = 100% |
| Safe Rejection Rate | 应拒绝的组中被拒绝的比例 | 必须 = 100% |
| Precision（发生替换时） | 替换中正确的比例 | 必须 = 100% |
| 分母为 0 | 没有可拒绝组/没有替换 | 记 `n/a`，不记 100%，不自动通过 |
| 零替换 | 没有发生替换 | 不能据此宣称阶段安全通过；必须报告原因与证据 |
| 版本不一致 | 源码哈希不符 | 标记 `version-mismatch`；不做位置级比较；不计入通过 |
| 旧构建结果 | `dist` 摘要与源码输入不匹配 | 不得用于新源码验收 |

**回归出口：** 阶段六必须把上述指标逐条列入最终报告；没有数据的项写 `n/a` 并说明原因。
